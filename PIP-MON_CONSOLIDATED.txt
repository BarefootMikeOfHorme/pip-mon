 2. POSITIONING - THE DECIDED LINE
  [DECIDED]
================================================================================

  PIP-MON replaces the layer that EXTENDS AND INTERACTS WITH Papyrus, not
  Papyrus itself.

  NOT REPLACED (native to the game; we target it)
    - The Papyrus VM and its .pex bytecode
    - Plugin container formats we must read (.esp/.esm/.esl)
    - The Creation Kit record format
    - Fallout4.exe

  REPLACED (this is the actual job)
    - F4SE and its plugin/addon ecosystem
    - Papyrus-extender frameworks (po3 and equivalents)
    - Garden of Eden and its plugin family
    - PAP and comparable papyrus helper frameworks
    - MCM, Buffout 4, and other in-game utility layers
    - Kinggath's Canary save-health script
    - Standalone papyrus script packs and the conventions they set

  INSPIRATION ONLY - ideas taken, no code, no dependency, no identity
    - AOB / signature-scanning methodology
    - Relocation-database concepts (static RVA per build + scan fallback)
    - Console command and script-property API design
    - Load-order conflict resolution techniques
    - SKSE::Trampoline-style inline detour technique (see 9.2)
    - The premise that a papyrus debugger is worth having

  WHY THIS MATTERS
    A dependency is a liveness obligation. If F4SE stops being maintained and
    PIP-MON is built on F4SE, PIP-MON dies with it. PIP-MON is meant to
    outlive everything it learns from.

  CURRENT REALITY - STATED PLAINLY
    F4SE is a HARD RUNTIME DEPENDENCY TODAY. vprobe.dll exports
    F4SEAPI_MakePluginInfo and is loaded from Data/F4SE/Plugins/. Known gap,
    tracked, with a removal path in section 13.

    GoE, PAP, MCM, Buffout: referenced NOWHERE in the codebase. Zero code,
    zero config parsing, zero asset reuse.

    CommonLibF4 / AddressLib: appear in vprobe/CMakeLists.txt as OPTIONAL
    FetchContent. Current sources are self-contained and link neither. The
    relocation-INI concept is borrowed; the code is unused.

    F4SE is retained FOR TESTING as the only way to load a plugin today.
    It is scaffolding, not architecture.

  THE CO-EXISTENCE ARGUMENT (from "clarification of separation")
    Multiple in-process extenders hooking the same process step on each
    other's vtable pointers -> undefined behaviour and CTD. This is the
    strongest technical argument for replacement: coexistence is not merely
    inelegant, it is unsafe.

 3. ARCHITECTURE - DUAL-MODE EVENT BUS
  [DESIGNED]
================================================================================

  Three tiers. The bus is the seam between them, and the seam is the whole
  design.

  +-------------------------------------------------------------+
  |  INTERNAL - in-process producer                             |
  |  [ Fallout4.exe ] -> [ vprobe.dll ] -> [ lockless ring ]    |
  +-------------------------------+-----------------------------+
                                  |  fast binary, raw structs
                                  v
  +-------------------------------------------------------------+
  |  EXTERNAL - hub / broker / daemon                           |
  |  [ Native IPC broker ]  (survives the game's death)          |
  +----------+-----------------------------------+--------------+
             |                                   |
             v                                   v
  +----------------------------+  +----------------------------+
  | LIGHTWEIGHT MODE            |  | WORKSPACE MODE              |
  | - micro TUI / system-tray   |  | - Actionable Error List      |
  | - high-level telemetry      |  | - FormID Inspector           |
  | - near 0% CPU, 0 MB VRAM    |  | - AI agent pipeline          |
  | - ~1 Hz subscription        |  | - full-verbosity logs        |
  +----------------------------+  | - plugin matrix, DAG, save   |
                                    +----------------------------+

  WHY TWO EXTERNAL MODES
    A full IDE-class workspace during gameplay costs attention and, on a
    heavy load order, costs frame budget. The lightweight mode exists so the
    user can keep the monitor up while playing. Both read the same bus, so
    they cannot disagree about what happened.

  THE THREE STATED BENEFITS (preserved verbatim in intent)
    1. DECOUPLED CRASH PROTECTION
       The game CTDs, the in-process probe dies, but the hub and monitor
       survive and hold the exact final stack trace / AOB hit to the
       millisecond. This is the single most important property of the
       architecture and is why the broker is a separate process rather than
       a thread inside the consumer UI.
    2. SELECTIVE SUBSCRIBER RATE
       Light monitor at 1 Hz for status; workspace subscribes to full
       verbosity only when focused.
    3. MULTI-CLIENT FLEXIBILITY
       Light HUD, file logger, and AI terminal pipeline can all attach
       simultaneously with zero game-side changes.

  PERFOMANCE RULE (non-negotiable, inherited from Rule 1)
    The in-process producer NEVER parses strings, formats text, or
    allocates on a game thread. It captures pointers, memcpy's packed
    structs into a lockless ring, and returns. All parsing, grouping, and
    rendering happens in the external tier.


================================================================================
 4. NATIVE ENGINE INTERACTION POINTS (what we hook, and why)
  [DESIGNED / partially BUILT+TESTED]
================================================================================

  4.1 ENGINE THREAD TOPOLOGY
      Main/Render   frame pacing, scene graph, Scaleform
      Job threads   TaskScheduler queue: collision, AI pathing
      Papyrus pool  bytecode execution, event queues, script state

      Consequence for us: hooking a Papyrus thread or the render loop to
      "just log it" is what causes micro-stutters in traditional tools. We
      tap memory through SEH-protected reads and publish to a lockless ring,
      so telemetry volume cannot affect frame pacing.

  4.2 FORMID INDEXING
      [0xAA] [0xBBBBBB]   8-bit plugin index (0x00-0xFE) + 24-bit object id
      Light plugins subdivide a slot byte into 4,096 sub-slots (0x000-0xFFF)

      >> CONTRADICTION C8 (section 12): two source files state the light
         marker differently (0xFE vs 0xFD). Needs verification against the
         engine before KaDag implements it.

  4.3 THE "RULE OF ONE"
      The engine parses active plugins top-to-bottom; the last writer of a
      FormID wins the runtime pointer. Consequences we must respect:
        - Any tool inspecting a FormID must resolve the WINNING record
          through the active load order, never the vanilla base value.
        - Overriding a record without updating its dependents breaks engine
          assumptions. Canonical case in 4.5.

  4.4 PAPYRUS SAVE MECHANICS (the basis of Canary Redux)
      1. Engine calls SaveGame()
      2. VM pauses and serialises: active thread stacks (frame variables,
         call stacks), unattached script instances, global and array heaps
      3. A delta of changed world forms is written alongside
      4. If the VM queue is deep (>50 pending events) or a thread is
         suspended mid-execution, half-executed states and orphaned handles
         are permanently BAKED into the save
      5. On load, those states cause infinite loops or an immediate CTD

  4.5 OCCLUSION - PRECOMBINE / PREVIS
      PRKC precombined meshes fold dozens of statics into one draw call.
      .vis precomputed occlusion decides what is visible from any point.
      Modifying one static in a cell without regenerating both breaks the
      reference: the engine falls back to hundreds of individual draws and
      disables occlusion -> massive FPS loss or invisible geometry.
      This is one of the most common "invisible wall" reports in FO4 and is
      NOT a papyrus problem, so the profiler must not blame papyrus for it.
      Response: flag cell record overrides lacking matching PRKC/.vis data,
      and correlate draw-call spikes at cell transitions to previs mismatches
      rather than to hook latency.

  4.6 SUMMARY MAP
      Subsystem          Native issue                 Our response
      -----------------  ----------------------------  ---------------------
      Papyrus VM         stack overflow, baked state   Canary Redux valve
      Data handler       silent "Rule of One" damage   KaDag record DAG
      Occlusion          broken geometry, draw spikes  PRKC conflict scanner
      Save serialisation corrupt .fos header arrays   out-of-process repair
      IPC / profiling    in-process logging stutters   lockless ring + IOCP

  4.7 ENGINE FAMILY LINEAGE - AND OUR STRATEGY BOUNDARY
      Skyrim (32-bit / SE) -> Fallout 4 -> Starfield are evolutionary
      variants of the same Creation Engine (Gamebryo lineage). They share
      the Papyrus VM architecture, the .PEX bytecode format, and the FormID
      reference-array rules. What Fallout 4 ADDS on top:
        - light plugins, with the slot-byte subdivision (see C8)
        - precombined geometry / Previs occlusion groups (PRKC)
      Practical consequence: a hook, a parser, or a rule written for one
      tends to work for the others, which is why the design stays
      Creation-Engine-anchored rather than Fallout-4-only.

      STRATEGY BOUNDARY (deliberate, do not erode):
        - Primary target is strictly Creation Engine internals, raw memory
          structures, and Papyrus serialisation.
        - Cross-engine paradigms (Unity, Unreal) are ADOPTED AS CONCEPTS
          ONLY - arena allocation, lockless SPSC rings, build-profile
          thinking, contextual logging. No Unity or Unreal runtime
          dependency, no attempt to be engine-agnostic in code.
        - Skyrim modder paradigms we explicitly adopt as inspiration:
          SKSE / Engine Fixes (native patches instead of script
          workarounds), PO3 / PapyrusExtender (exposing native state to
          out-of-process tooling via zero-allocation reads), and Kinggath's
          Canary (save-health tracking as a first-class concept).


================================================================================
 5. IPC CONTRACT (V-LINK)
  [BUILT+TESTED]
================================================================================

  ENDPOINT    \\.\pipe\vlink_telemetry
  DIRECTION   vprobe -> dashboard (telemetry), dashboard -> vprobe (control)

  FRAME       [ 28-byte packed header ][ payload ]
              magic 'F4MO' | version | event type | flags | length | QPC | seq | tid
  ENCODING    binary packed struct, memcpy on the producer, struct.unpack_from
              or bytemuck on the consumer. No JSON, no CBOR, no msgpack.
  WHY         every serialisation format needs an ENCODER on the producer, and
              that encoder runs on a game thread. A memcpy costs nothing.
  STRINGS     interned u32 indices, never inline. One name table is sent per
              connection.
  PRIORITY    under back-pressure, shed VM_TICK first; never drop
              VM_EXCEPTION, STACK_DUMP or SAVE_BLOAT.

  FULL SPEC   docs/IPC_PROTOCOL.md
  All three language bindings assert the same sizes at compile time:
    C++     vprobe/include/TelemetryEvent.hpp   static_assert
    Python  overseer_cli/src/overseer_cli/protocol.py
    Rust    overseer_cli/rust/vlink-protocol     const assert

  CONTROL CHANNEL (Rule 3)
    Commands are queued and executed on the engine's main thread on the next
    frame. Never a synchronous reply. Order of preference for any action that
    can leave state half-written:
      1. soft cancel  (Script.Cancel)      safe, releases locals
      2. force kill   (VM thread purge)   gated behind explicit confirmation
    A force-kill can leave quest flags or workshop state half-written. That is
    unrecoverable, so it is a human decision, never an automatic one, and
    never an AI-agent action.

  >> CONTRADICTION C5 (section 12): the source docs specify a shared-memory
     mmap ring as the transport. We implemented a named pipe with an internal
     SPSC ring plus IOCP. The GAME-THREAD CONTRACT is identical (lockless ring,
     raw structs, drop on full); only the carrier differs. Resolution in C5.

        - an always-visible ANOMALIES (n) count, mirroring an IDE's
          PROBLEMS (0). Non-collapsible. A monitoring tool that can be
          silently silent is the failure mode we are engineering against.
        - a left activity rail for panel switching
        - collapsible sections with disclosure triangles
        - a tabbed bottom panel
        - a status bar that is never hidden
        - semantic colour: green ok / yellow warn / red critical, plus an
          always-visible text label so it does not rely on colour alone
        - row selection highlight
      Honest terminal limits, stated so nobody chases them:
        - no hover -> everything visible or reachable by key
        - right-click menus -> keybindings, shown in the footer
        - no minimap -> density must come from layout
        - no icon fonts -> severity gets a text glyph, not a pictogram
        - 8-colour-safe palettes must degrade to bold/dim

  6.2 TWO-PANE CLI ("dual engine" layout)
      +-- TOP: resizable interactive console ------------------------------+

      |   kill <ThreadID>   soft-cancel or force-purge a Papyrus thread     |

      +-------------------------------------------------------------------+
      +-- BOTTOM: fixed telemetry dashboard, ALWAYS VISIBLE ---------------+

  6.3 TAB STRUCTURE
      Tab 1  MONITOR     live threads, stacks, memory, event rate
      Tab 2  WORKSPACE   editor, AI pipeline, terminal
      Tab 3  PLUGINS
        page 1  ACTIVE LOAD ORDER   (see section 7)
        page 2  NATIVE LIBRARIES   (see section 10)
      Tab 4  CLI / TUI   pure headless mode

  6.4 LOG OBJECT MODEL (Unity-style contextual logging, adopted deliberately)
      Every log/diagnostic record carries FOUR fields, not one string:
        1. raw error text
        2. script / source path
        3. line and column
        4. target FormID
      Why: this is what makes one-click navigation possible from the
      Actionable Error List straight to the offending line in the upper
      workspace. A single opaque string cannot do that.

  6.5 EARLY-WARNING PARSER
      Creation Engine emits "Suspended stack count is over our warning
      threshold" BEFORE a crash. Parse that specific message in the bus and
      raise a high-priority alert ahead of the hard CTD.

  6.6 CLOAK-SCRIPT / POLLING DETECTOR
      Flag scripts that produce latency without a fatal error:
        - rapid OnUpdate() loops
        - high-frequency distance-check spatial scans ("cloak scripts")
      These are a papyrus problem and invisible to a crash logger.

  6.7 ACTIONABLE ERROR LIST - DEDUPLICATION
      Papyrus can emit 40MB+ of text in seconds during a loop or stack dump.
      Untreated, this freezes the UI watcher or exhausts RAM.
      Policy: hash each error. If the same hash exceeds 50/second, collapse
      it into ONE list entry with a live counter badge ("Error X [x1450]")
      and allocate no further rows.
      External third-party noise (missing textures and similar) is collapsed
      by the same pipeline so it never pollutes the actionable list.

  6.8 AI PAYLOAD HYGIENE
      "Send selected to AI" must NOT ship raw 500-line stack dumps. Extract
      only: the deduplicated atomic error item, the associated source snippet,
      and version deltas. Unfiltered dumps waste tokens and bury the signal
      in repetitive engine noise.

  6.9 OPTIONAL DETACHABLE HUD
      A borderless transparent overlay (WS_EX_TOPMOST / WS_EX_TRANSPARENT) is
      permitted as a display mode for the lightweight monitor. It must NEVER
      hook the DX11/DX12 swapchain, so it cannot clash with ENB, ReShade, or
      existing HUD mods. Terminal TUI remains the default.


================================================================================
 7. KADAG - LOAD ORDER, RECORDS, SAVE STATE
  [DESIGNED]
================================================================================

  7.1 CORE ALGORITHM
      Build a directed graph; topologically sort it; detect cycles.
        a. RECORD CONFLICT GRAPH
           For every (A,B) defining the same FormID, the later loader wins,
           so A must load first: edge A -> B. Derived from master-file
           version comparison, exactly as LOOT does.
        b. TOPOLOGICAL SORT - Kahn's algorithm. O(V+E), sub-millisecond.
        c. CYCLE DETECTION IS FREE
           Kahn's leaves any node with non-zero indegree; that remainder IS
           the cycle set. No separate traversal required.
        d. STABLE TIE-BREAKING (mandatory)
           A pure topological sort is non-deterministic. Order ties by:
           ESM before ESP, official DLC last, then alphabetical. Without this
           the load order reshuffles every run and users lose trust.

  7.2 SAVE-STATE CONTEXT SELECTOR
      Dropdown / hotkey overlay switching two modes:
        GLOBAL MODE     every file present in Data/
        SAVE-STATE MODE parse the selected .fos header, which carries a
                        length-prefixed array of the .esm/.esp/.esl files
                        active at the exact moment of saving
      Save-State Mode populates a two-sided actionable diff:
        EXPECTED BUT DISABLED   in the save, missing from the load order -> RED
        ACTIVE BUT UNUSED       in the load order, absent from the save -> YELLOW

  7.3 PLUGIN MATRIX (Vortex-style rows)
      Columns: state toggle | slot index (0x00-0xFE, light 0xFD:0x000) |
               plugin name | domain category | quick badges [Pin] [Previs!] [Sync]
      Hotkeys: Space toggle (staged only) | Shift+S sync to the selected save |
               Shift+D cycle detection across active edges
      >> CONTRADICTION C9: C7/KaDag choose Kahn (free cycle detection);
         this doc names Tarjan. See 12. Both are valid; resolution states
         when each is the better tool.

  7.4 FORMID INSPECTOR
      Read the WINNING override record from the active load order stack.
      Never report a vanilla base value as if it were live.

  7.5 MCM PARITY (feature we replace)
      MCM embeds ActionScript 2 / Scaleform in the render loop and stores its
      settings in the SAVE FILE - i.e. the config menu bloats every save and
      is coupled to the render thread. PIP-MON's replacement keeps all
      configuration in external JSONC files. No save-file footprint, no
      render-thread cost.

  7.6 WRITE POLICY - NON-DESTRUCTIVE BY CONSTRUCTION
      1. Toggles and syncs update an in-memory STAGED buffer
         (OvMonDat/staging/plugins.txt). Data/ is not touched.
      2. F4 APPLY is the only action that writes.
      3. A timestamped backup is written first:
         Data/plugins.txt.bak_YYYYMMDD_HHMMSS
      4. Only then is the staged file moved into place.
      A load-order brick is unrecoverable without manual file recovery, so
      nothing is ever written in place, and never from inside the game.

  7.7 ORPHANED DEPENDENCY ALERT
      Missing-master warnings surfaced as first-class findings, with the
      profile-sandbox framing: a save-state profile is an isolated target
      build configuration, not just a file.


================================================================================
 8. CANARY REDUX (THE KINGGATH PROTOCOL) - SAVE HEALTH
  [DESIGNED]
================================================================================

  8.1 WHAT IS BEING UPGRADED
      Kinggath's Canary is a passive papyrus script that polls variables.
      Canary Redux is a native pre-save hardware valve plus an external
      repair daemon. Zero papyrus overhead; the check happens at the engine
      layer. The original name and author are honoured in the naming.

  8.2 LAYER A - IN-PROCESS VALVE
      Hook native SaveGame().
      Poll PapyrusVM::GetNumPendingEvents() at the engine pointer level.
      If pending events exceed 50, HOLD the save thread for up to 1500 ms to
      let the VM drain. Release only when:
        - VM stack depth == 0 (quiescent)
        - no orphaned/deleted FormIDs among active handles
        - Win32 file-handle lock guard passes
      If the drain does not complete within the hold window, the save
      proceeds and is marked UNSECURE rather than hanging the game.

  8.3 LAYER B - OUT-OF-PROCESS REPAIR DAEMON
      Parses the newly written .fos asynchronously, then:
        1. FORMID REMAPPING
           Shift orphaned FormID prefixes when plugins were reordered or
           removed - the difference between loading and an instant CTD.
        2. UNATTACHED INSTANCE PRUNING
           Purge dead script instances pointing at missing base forms
           (FormID == 0x00000000).
        3. HEAP SANITISATION
           Truncate bloated script arrays (>10,000 indices) and recompute
           chunk byte counts.
      On FAIL: quarantine immediately, produce Save_N_Repaired.fos, write a
      timestamped Save_N.fos.bak, and alert the user BEFORE the next load.
      On PASS: mark SECURE.
      The repair daemon is a SEPARATE process from the game, so a repair bug
      cannot corrupt a live session - only a copy on disk.

  8.4 LIVE WIDGET (header strip)
      CANARY REDUX:  <state>  |  VM Stack: 0/<limit>  |  Save Readiness: [SECURE]
      Last Save Check: <file> (Passed Nms) | Active Remaps: N | Orphans: N

      >> CONTRADICTION C6: this widget was specced as "VM Stack: 0/128" but
         Papyrus' real stack limit is 0x400 (1024). The 128 is almost certainly
         a typo carried through several documents. See 12.


================================================================================
 9. INDEPENDENT ANALYSIS OF A LEGACY EXTENDER
  [DECIDED - record only]
================================================================================

  Kept in the record because it explains WHY our architecture looks the way it
  does, and because three of its conclusions are things we deliberately kept.

  9.1 THE LOADER
      A legacy loader is a small Win32 wrapper (~50-100 KB) that calls
      CreateProcessW in a suspended state, allocates a region in the target,
      injects the core DLL, and runs a remote thread to force-load it.
      Conclusion drawn: that approach trips modern anti-cheat heuristics and
      breaks on every executable hash change. We want a streamlined
      static dynamic-link structure that hooks cleanly at init.
      >> This conclusion is exactly the argument for the F4SE-independence
         roadmap in 13. Today's vprobe.dll is loaded BY f4se_loader, which
         means it currently carries the problem it set out to avoid.

  9.2 THE CORE API AND ADDRESS LIBRARY  [TECHNIQUE KEPT]
      A legacy core is a very large C++ codebase (100k+ lines) of structural
      class definitions, which shifts with every game update, so it resolves
      offsets through an ID-keyed address database.
      Conclusion drawn, and this is the right call:
        - KEEP the dynamic-address-resolution idea
        - DROP the class hierarchies; map only the pointers actually needed
          (SaveGame, PapyrusVM state, ring queues)
      Consequence: vprobe is a few thousand lines, not 100k.

  9.3 TRAMPOLINES AND HOOKING  [TECHNIQUE KEPT]
      A legacy hook allocates a small executable memory cave (64-512 bytes)
      near the code segment and writes JMP overrides redirecting to a native
      handler.
      Conclusion drawn: this exact technique is correct for us, and is what
      vprobe's Detour layer implements. Minimum viable relocation is the whole
      game.

  9.4 THE PIPELINE SHIFT
      Monolithic C++ SDK linking
        -> C++ strictly confined to the in-process memory bridge; all heavy
           logic out-of-process.
      Synchronous papyrus function registration
        -> we own the script API instead of inheriting someone else's
           (see C7 - the source docs say "remove custom script functions from
           the VM entirely", which we read as "remove THEIR registration",
           not "remove the capability").
      In-process crash exposure
        -> parsing, DAG work and diagnostics out-of-process, so a tool bug
           can never crash the game.


================================================================================
 10. LIBRARY AND TOOL INVENTORY
  [DECIDED - record only]
================================================================================

  10.1 SECTION A - READABLE SOURCE / HIGHER-LEVEL
       Mutagen (C#, CLI bridge)
         record generation, AST script parsing, declarative mod edits;
         produces typed intermediate representations for KaDAG without ever
         executing papyrus on a game thread.
       LOOT / libloadorder / esplugin (Rust)
         ASCII load-order evaluation, topological sorting, .esp/.esm/.esl
         header flags, light-slot (0xFE) reading, sub-millisecond sorts.
         >> See C7 on whether we call loot-cli or ship our own sort.
       Champollion / PEX decompiler (C++ / Rust)
         compiled .pex bytecode -> readable .psc. Used for live inspection of
         a locked thread: decompile the offending script on the fly to pin
         the exact function call.
       Caprica (Papyrus compiler)
         the forward compile path behind the CLI's `compile <file>`.

  10.2 SECTION B - RAW BINARY / MEMORY / CRASH
       rust-minidump / minidump-stackwalk
         parse native Windows .dmp and walk the stack. On a CTD, extract the
         faulting address, loaded DLL and instruction pointer with no debugger
         attached - which is what makes post-mortem useful.
       zlib-ng / flate2
         zero-copy decompression of compressed chunks inside .fos saves;
         sub-millisecond header inspection of script heaps.
       zerocopy / byteorder (Rust)
         direct casting of raw bytes into typed structs with no allocation.
         NOTE: we chose bytemuck for V-Link; zerocopy remains a candidate for
         the save-file slice reader.
       Capstone
         disassembly around SaveGame and PapyrusVM vtables, avoiding
         hardcoded offsets across updates.
         NOTE: vprobe currently uses Zydis, which is a strict superset of
         Capstone's disassembly and is what the detour layer needs for exact
         instruction LENGTH. Either is acceptable; Zydis is the current choice.

  10.3 SECTION C - UNIFIED PIPELINE (three layers)
       LAYER 1  RAW BINARY / MEMORY  (in-process)
         vprobe -> (bus) -> byte slices -> typed structs
       LAYER 2  READABLE SOURCE & DAG  (daemon)
         esplugin    -> record graph matrix (KaDag)
         Champollion -> faulting stack decompiled .pex -> .psc
         minidump    -> native fault addresses symbolicated to module offsets
       LAYER 3  TERMINAL UI
         live buffer bandwidth and byte read rates
         highlighted faulting .psc lines, active native library bindings

  10.4 LANGUAGE PORTFOLIO
       The protocol is language-neutral by construction: the wire format is
       three parallel declarations (C++ / Python / Rust) held in sync by
       compile-time size assertions.
       C++      in-process probe only. Confined to the memory bridge.
       Rust      the vlink-protocol ABI crate is COMPLETE and tested
                 (5 tests, forbid(unsafe_code)).
       Python    the reference implementation of the external tier, chosen
                 because the analysis layer changes far more often than the
                 probe and must ship without a compiler.
       >> C1: several source docs specify Rust/Ratatui for the external tier.
          Recorded as a valid alternative rather than a contradiction, because
          the ABI was built to permit it.


================================================================================
 11. PITFALLS AND SAFEGUARDS (consolidated, all six)
  [DECIDED]
================================================================================

  P1  IN-PROCESS BUS OVERHEAD -> MICRO-STUTTERS
      Risk    string formatting or file I/O in the game process starves
              the frame or engine threads.
      Guard   producer thread fully asynchronous; lockless ring; raw binary;
              ALL parsing, line grouping and UI generation external.

  P2  PAPYRUS LOG BUFFER FLOODING
      Risk    40MB+ of text in seconds; UI watcher freezes or RAM exhausts.
      Guard   hash dedup; >50/sec collapses to one entry with a live counter
              badge, no new list rows. (See 6.7.)

  P3  UNSAFE MEMORY READS DURING LIVE SCANNING
      Risk    scanning the executable while the game runs can raise
              0xC0000005 or crash the process.
      Guard   SEH (__try/__except) plus VirtualQuery page-attribute checks
              before reading. vprobe's DynamicScanner does both: it refuses
              matches that cross a page boundary, that are not inside an
              executable section, or that fail a function-prologue check.

  P4  AI CONTEXT OVER-SATURATION
      Risk    raw stack dumps waste tokens and confuse the model.
      Guard   extract only the deduped atomic item + source snippet + version
              delta. (See 6.8.)

  P5  NON-SCRIPT MOD INTERFERENCE
      Risk    false positives: blaming papyrus or our hook for problems
              caused by texture, mesh, cell, lighting, or NPC mods.
      Guard   read-only relative to third-party plugin structures - never
              mutate another mod's data in memory; classify draw-call and
              NPC-spawn spikes by their actual cause (previs mismatch,
              FaceGen mismatch) instead of reporting them as engine faults.

  P6  SAVE-STATE DESYNCHRONISATION
      Risk    force-terminating a papyrus thread leaves quest variables or
              workshop state half-written; the save is silently wrong.
      Guard   soft cancel first, always; force kill requires explicit
              confirmation AND a save-to-new-slot warning; the detector never
              auto-remediates - it reports. A monitoring tool that silently
              changes game state is a liability.

  COMPATIBILITY MATRIX (from the mod-conflict analysis)
      Mod category            Risk    Handling
      -----------------------  ------  ---------------------------------------
      Texture & mesh packs     VERY LOW  dedup missing-file warnings
      Worldspace & cell mods   MEDIUM    flag previs/precombine mismatches
      Lighting & weather mods  LOW       resolve winning FormID overrides
      UI / HUD overlays        LOW       borderless OS overlay, no DX hook
      Body / NPC overhauls     LOW       isolate FaceGen stutter from hook cost

  DETECTION COVERAGE SUMMARY
      Previs / precombine   cell record overridden without regenerated
                            PRKC/.vis -> invisible geometry, draw spikes
      FormID overrides      winning record must be resolved through the live
                            load order, not the vanilla base
      Loose vs BA2          loose files raise I/O and memory; isolate so the
                            bus is not starved
      FaceGen / tint        NPC_ record changes without matching pre-baked
                            geometry -> micro-stutter on spawn; tag as
                            "FaceGen Mismatch", not hook latency

 12. CONTRADICTIONS FOUND - AND HOW EACH IS RESOLVED
  [OPEN]
================================================================================

  Read this before building anything in sections 6-8.

  C1  LANGUAGE: Rust/Ratatui vs Python/Textual
      Source     most docs specify Rust; the build is Python/Textual.
      Resolution NOT a contradiction. The wire ABI was designed to be
                language-neutral and the Rust crate is complete and tested.
                Python is the reference implementation; the Rust port is a
                supported alternative. Rule: any shared logic must live in
                the protocol, never in UI code.

  C2  F4SE: "we do not co-exist with or rely on F4SE" vs current reality
      Source     "clarification of separation" states the rule; the built
                 plugin is an F4SE plugin.
      Resolution The rule is correct and the current state is a KNOWN GAP,
                not an exception to the rule. F4SE is test scaffolding.
                Removal path in 13. Build toward the rule.

  C3  LOOT: call loot-cli vs ship our own sorter
      Source     the save-state doc integrates `loot-cli.exe` as a subprocess;
                 KaDag describes our own DAG sorter.
      Resolution BOTH, with a decision rule. Default: our own graph, because
                it is the replacement and it owns the record-level detail
                (PRKC, FaceGen, dirty-record) that LOOT does not model.
                loot-cli is a FALLBACK ADAPTER for users who want upstream
                LOOT's curated rule set, invoked as a subprocess.
                Subprocess-only, never linked: LOOT is GPLv3 and PIP-MON is
                MIT, so linking it would contaminate the licence.
                This preserves the "MIT/GPLv3 separation" intent in the
                save-state doc AND the replacement goal.

  C4  TRANSPORT: shared memory (mmap) vs named pipe
      Source     docs specify a lockless mmap ring; we built a named pipe
                 with an internal SPSC ring + IOCP.
      Resolution The GAME-THREAD CONTRACT is identical either way - lockless
                ring, raw packed structs, drop on full, all I/O owned by a
                worker. Only the carrier differs. Named pipe was chosen
                because it needs no shared-memory handle lifetime management
                across process restarts, which matters for crash survival
                (P6 / benefit 1). Shared memory can be added as a SECOND
                transport on the same internal ring later; the format does
                not change.

  C5  PIPE NAME: \\.\pipe\Fallout4DebugBus vs \\.\pipe\vlink_telemetry
      Source     the dual-mode bus doc names a different pipe.
      Resolution V-Link is the named API; the pipe is its endpoint. Keep
                vlink_telemetry. Recorded so nobody "fixes" it back.

  C6  VM STACK LIMIT: 0/128 vs 0x400 (1024)
      Source     the Canary widget spec says 0/128; the VM's real limit is
                 0x400.
      Resolution 128 is a typo propagated across documents. The limit is
                1024, the warn line is 820, and the wire format carries depth
                as u16 BECAUSE 128/255 cannot represent 1024 - a real bug that
                shipped in our first draft and was caught by the test suite.
                Any threshold doc showing 128 is stale.

  C7  SCRIPT FUNCTIONS: "remove from the VM entirely" vs an in-game API
      Source     the source-analysis doc says remove custom script functions
                 from the VM; other docs want an in-game console, an event
                 bridge, and developer-facing Papyrus bindings.
      Resolution The former means "stop inheriting the legacy extender's
                registration", not "remove the capability". We replace THEIR
                script API with OUR OWN. PIP-MON's script surface is a
                deliberate replacement capability, and a differentiator from
                every legacy tool.

  C8  LIGHT PLUGINS: 0xFE subdivision vs 0xFD
      Source     one doc says 0xFE subdivides into 4,096 slots; another shows
                 the column as "0xFD:0x000".
      Resolution UNVERIFIED. Fallout 4 treats both 0xFD and 0xFE as light
                markers with differing subdivision rules. Must be read out of
                the engine, not out of these documents. Blocks KaDag's slot
                handling until confirmed. Flagged, not silently resolved.

  C9  CYCLE DETECTION: Kahn vs Tarjan
      Source     the save-state doc binds Shift+D to Tarjan; KaDag uses
                Kahn's.
      Resolution Both correct, different tools. Kahn's gives cycle detection
                for free as its leftover set and is the primary sorter.
                Tarjan's SCC decomposition is the better choice when the UI
                must SHOW the user which plugins form a cycle, because it
                yields the strongly-connected components directly. Use Kahn to
                sort, Tarjan to explain.

  C10 RUNTIME: "remove custom script functions" vs in-game console
      See C7 - same issue, recorded once. Kept as a separate row because it
                appeared in two files with different wording.

  C11 OVERLAY: transparent overlay window vs "zero in-game UI"
      Source     the compatibility doc permits a transparent overlay; other
                 docs insist on zero in-game rendering.
      Resolution Compatible once scoped. The overlay is an optional DISPLAY
                mode for the lightweight monitor, drawn by the OS
                (WS_EX_TOPMOST / WS_EX_TRANSPARENT) and never by hooking the
                DX swapchain. The workspace mode is terminal-only. Both are
                out-of-process; neither injects a renderer.

  C12 ANTI-CHEAT: "manual injection triggers anti-cheat" vs we are injected
      Source     the source-analysis doc flags loader-and-inject as a problem;
                 we are loaded by an injector.
      Resolution Same as C2. It is an argument for the removal path, and an
                honest reason not to ship a F4SE-style loader as our own
                answer.

  C13 SAFE/LANGUAGE CLAIM: "Rust guarantees memory safety" vs probe is C++
      Source     one doc claims Rust safety with unsafe confined to probes;
                 the probe is in fact C++.
      Resolution Restate accurately: C++ is confined to the in-process
                bridge and is the part where the language offers no
                guarantees, which is precisely why the volume of C++ is kept
                minimal. All data handling is out-of-process, and the Rust
                crates are forbid(unsafe_code). The claim was directionally
                right and literally misattributed.

  C14 CREATION KIT: listed as a replacement target vs it is not replaceable
      Source     "1moreideas" targets "Creation Kit / G.E.C.K." and "Creation
                 Kit Platform Extended" as part of the dual-pipeline
                 replacement.
      Resolution NOT REPLACEABLE, and the doc should not imply otherwise. The
                CK is closed-source, GUI, and out of scope for a telemetry and
                script-workstation project. We consume its FILE FORMATS; the
                tool itself stays. Attempting it would consume the entire
                project. See 15.2-15.3.

  C15 ENGINE FIXES: "High FPS Physics Fix / Tweaks" listed under runtime tools
      Source     the same file groups gameplay fixes with tooling and assigns
                 "KaDag handles pre-combine and asset validation" as the
                 replacement for the whole row.
      Resolution Category error. High FPS Physics Fix is a PHYSICS correction,
                not a tool; we do not replace it and should not claim to. Our
                replacement column is correct for PRP (pre-combine repair) and
                wrong for the rest of that row. Gameplay fixes are out of
                scope by definition - we diagnose, we do not rebalance.

  C16 MCM SETTINGS: no replacement assigned
      Source     MCM and Scaleform have a replacement; "MCM Settings Manager /
                 Setting Loaders" is listed with none.
      Resolution Assigned here: external JSONC configuration, already the
                design for vprobe_settings.jsonc and overseer_rules.jsonc. The
                specific advantage to state is that legacy MCM settings live
                INSIDE the save file, so the config menu bloats every save;
                ours costs nothing in the save and never touches the render
                thread.

  C17 .ba2 SCOPE: Archive2 replacement implies writing archives
      Source     "Archive2.exe" listed as a replacement target; KaDag is
                 described as a "BA2 validator".
      Resolution Split by direction. READING .ba2 (to validate that loose files
                and archives agree, per section 11) is in scope and needed.
                WRITING new .ba2 archives is not in scope and would be a
                separate multi-month project. Validator only. See 15.2.

  C18 UNITY TOOLCHAIN: adjacent workflow vs the engine-agnosticism boundary
      Source     the Unity / procedural-generation reference proposes a
                 translation bridge producing ".ba2 / Unity asset bundle
                 wrappers".
      Resolution Not a boundary violation, because Unity is a SEPARATE
                EXTERNAL PROCESS, not a dependency - section 4.7's "no Unity
                runtime dependency" still holds. But the wording brushes
                against two settled lines:
                  - a general asset CONVERTER is content authoring, out of
                    scope per 15.3 / C14
                  - WRITING .ba2 is out of scope per C17
                Resolution: support READING the open interchange formats
                (.obj/.fbx/.step/.stl), geometry sanity checks, and
                provenance tracking; refuse converters and archive writing.
                Scoped in 17.3, line stated in 17.4.

  C20 xEdit SCOPE: "replacing xEdit" includes record patching
      Source     item 8 of the replace-list names FO4Edit, whose headline
                 capability is writing a patched .esp that resolves conflicts.
      Resolution Split by direction, on the read/write asymmetry in the
                replace-map: load-order analysis and conflict REPORTING are in
                scope and useful (KaDag). Patch GENERATION is out. A writer
                must be byte-exact or the game silently misloads, and that
                surface is a decade of edge cases in override/filter records
                and parent-ESM inheritance. We diagnose conflicts; we do not
                rewrite records.

  C19 REFERENCE PROVENANCE: a hand-pasted source is truncated
      Source     the Unity reference arrived pasted by hand, ending in a
                 stray rule and a cut-off table.
      Resolution Section 17 records the INTENT and flags the truncation as
                Q9. Nothing was invented to fill the gap. If more of that
                document exists, it should be reviewed against 17 before
                anything in it is built.

 18. THE SURVEY, THE PROVIDER REGISTRY, AND DEPLOY LIFECYCLE
   [DESIGNED - location map VERIFIED on a real install; nothing built yet]
================================================================================

  WHY THIS SECTION EXISTS
    It is the concrete form of A1 (the mod-manager VFS blind spot), and it
    exists because of a specific evening. A game was reported as "F4SE is
    broken". Three subsystems were investigated in turn -- F4SE, Papyrus, then
    the mod manager -- and the actual cause was that the mod manager's state
    directory had been deleted, so the game was loading an install whose load
    order no longer existed. Nothing anywhere reported that contradiction. The
    failure was not exotic; it was four sources of truth disagreeing and no
    component whose job it was to notice.

  18.1 THERE IS NO SINGLE ANSWER TO "WHAT IS ACTIVE"
      Each provider has its own notion, its own storage, and its own idea of
      truth. This map was verified by reading a real installation, not recalled.

      PROVIDER      STORAGE                        WHAT IT BELIEVES
      ----------    ----------------------------    ---------------------
      Bethesda      <game>\Data\                    the files that exist
      Bethesda      <user>\Documents\My Games\...  saves, prefs, config
      F4SE          <game>\Data\F4SE\              the plugin load order
      F4SE          <user>\Documents\...\F4SE\    per-plugin state, logs
      Vortex        %APPDATA%\Vortex\state.v2\     which mods are enabled
      Vortex        %APPDATA%\Vortex\<game>\mods\ installed mod folders
      MO2           Documents\MO2\profiles\         instance contents
      FOMOD         <mod>\fomod\modlist.xml        what the installer did

      Observed on the reference install:
        <game>\Data                569 entries (plugins, archives)
        <user>\Saves                80 files
        <game>\Data\F4SE\Plugins    46 entries (third-party DLLs)
        %APPDATA%\Vortex\<game>\mods  68 mod folders
        MO2 / FOMOD: not installed, so presence-checked only

  18.2 THE PROVIDER REGISTRY
      Each mod manager and installer framework is a PROVIDER behind one small
      uniform contract. The contract is deliberately three questions, because
      each of them has already turned out to matter:

        probe()           -- is this provider present, and can we read it?
        enabledSet()      -- what does it CLAIM is active?
        disagreements()   -- where does that contradict another provider?

      The third is the product. The evening's failure produced exactly one
      line of useful output -- "Vortex reports 65 enabled, the game directory
      contains 0 deployed plugins" -- and computing it takes seconds once the
      adapters exist. A diagnostic that says that is worth more than any
      amount of log archaeology.

      PROVIDERS READ ONLY. Never write, never reconcile, never repair. That is
      what keeps the coexistence contract intact, and it means adding a fourth
      mod manager is a new adapter rather than a change to the core.

  18.3 THE SURVEY, PUBLISHED AS DATA
      Not a service other things ask. A MANIFEST: a versioned snapshot of what
      is installed, where, and which provider is authoritative. The
      out-of-process tier builds it; the in-process tier reads it.

        KaDag/overseer (out)          vprobe (in)
          detect providers              reads the manifest at INIT,
          survey locations              on its own worker thread
          build manifest
          publish -------------------------^

      The in-process side reading a file is permitted, and the reason matters:
      init is NOT a game thread. It is our own worker, which exists precisely
      so that file I/O, database parsing, and address derivation never touch
      game threads. The rule forbids file I/O ON GAME THREADS; reading a
      manifest at init is the case the rule was written to permit.

      DOUBLE-CHECK EVEN WHEN THE PROGRAM THINKS IT KNOWS.
      This is the load-bearing requirement, not a nicety. The manifest is a
      cache WITH A VERIFICATION CONTRACT, not a cache that is trusted:
        - it carries a GENERATION HASH over its inputs
        - a consumer RE-VALIDATES the specific entries it uses
        - a consumer that is working from a stale generation SAYS SO rather
          than proceeding quietly
      A stale manifest therefore costs a re-survey, never a wrong answer.

      The survey is re-runnable ON DEMAND. Nothing polls.

  18.4 ONE NUMBER, THREE JOBS
      The generation hash is computed over (game build, provider set, load
      order). That single value is:
        - the key of the HOOK MAP from section 18.6
        - the input to the DRIFT DETECTOR
        - the manifest FRESHNESS token
      One concept doing three jobs, instead of three mechanisms that can
      disagree with each other. This is the part worth getting right, because
      the alternative -- a hook-map key, a drift check, and a manifest
      timestamp maintained separately -- will eventually disagree, and the
      disagreement will be invisible.

  18.5 DEPLOY AND EJECT
      [PROPOSED - none of this is built]
      Staging is currently two manual file copies, and it has already failed
      once in the obvious way: the target DLL could not be overwritten because
      the game was still running with it loaded. That is not an annoyance, it
      is information -- a DLL with a live thread in it cannot be replaced, and
      attempting to is a real failure mode rather than a file lock to retry.

      EJECT    -- inventory what WE placed, by manifest, and remove exactly
                  those paths. Never a glob, never a directory sweep. A
                  sweep is the mistake described in G15.
      DEPLOY   -- refuse if the target is in use, place the files, then
                  RE-RUN THE VALIDATION SUITE and report. A deploy that has
                  not been validated is an unverified claim.
      REDEPLOY -- eject then deploy, as one operation, so the intermediate
                  state is never observable.

      PROCESS SHUTDOWN POLICY -- the part that needs a decision, and the part
      that is deliberately NOT automated:
        - processes WE started are cleaned up automatically, always
        - the user's game is NEVER terminated without asking
      This is the same line already drawn for auto-restart during play. A tool
      that kills someone's game unprompted is a tool people uninstall, and
      the user's own time in the project makes that boundary a hard one here.
      Proposed behaviour: DETECT and REFUSE by default, with an explicit
      opt-in to shut down, and never a silent kill.

  18.6 WHAT THIS DOES NOT SOLVE YET
      Still [DESIGNED] throughout. No adapter is written, no manifest exists,
      and the deploy tooling does not exist. The location map is verified; the
      mechanisms built on top of it are not.

================================================================================
 19. IN-PROGRAM ARCHITECTURE: SAVE LINEAGE, TRIAGE, AND THE SAFE WINDOW
   [DESIGNED - this is the program's internal structure, not a feature list]
================================================================================

  WHAT THIS SECTION IS, AND IS NOT
    This is how the runtime is ORGANISED INTERNALLY, not a list of things to
    build. Nothing here is scheduled work. It is recorded now because it is
    decided rather than half-remembered, and because a future session reading
    only the roadmap would otherwise invent a different model and find it
    incompatible.

    It is also explicitly DOWNSTREAM of capture working. Trace capability means
    "what happened before this save", and nothing is being captured yet, so
    none of this is buildable until the hook layer is proven. Writing it down
    now is preparation, not progress.

  19.1 SAVES ARE A LINEAGE, NOT A PILE
      The on-disk naming already encodes one, which is how the model was
      recognised rather than invented:

        Exitsave0_<formID>_<location>_<form>_<index>_<n>_<stamp>.fos
        Save1..Save12_<same formID>_...        a per-character chain
        Autosave1..3_<formID>_...              a rolling window

      Two properties follow, and both are load-bearing:

      SEMI-MUTABLE. A save file, once written, is effectively immutable -- but
      the CHAIN around it mutates: slots fill, the active save moves, an
      exitsave is superseded. So the structure is mutable and the nodes are
      not, which is the awkward case that most tools get wrong by treating
      each file as independent.

      NOT-WHILE-GAME-RUNNING. Save state is not mutated while the game holds
      it. This is the same class of rule as the DLL lock already encountered:
      a file the game is using cannot be treated as settled. It is stated here
      as an architectural property rather than an error to catch later.

  19.2 TRIAGE IS REASONING OVER THE LINEAGE, NOT A FEATURE
      Triage is a capability the runtime has, not a tool we build for users.
      It operates at two levels, and the second is the one that only exists
      because of the lineage:

        NODE HEALTH      -- is this save internally valid? readable header,
                           intact structure.
        LINEAGE HEALTH   -- is the CHAIN intact? A chain can be broken while
                           every node in it is individually valid: a missing
                           Save4 between Save3 and Save5, a Save1 whose
                           timestamp precedes its parent, an Exitsave0 that
                           follows no prior save. Node validity cannot detect
                           any of that. Sequence can.

      Classes, and the rule that matters most:
        healthy     node valid, chain continuous        -- no action
        suspicious  valid node, odd lineage             -- report
        orphaned    no parent chain, or sequence and
                    timestamp disagree                  -- report
        corrupt     unparseable or truncated            -- the ONLY class that
                                                          could justify action

      TRIAGE REPORTS. IT NEVER ACTS. A tool that decides a save is corrupt and
      then offers to repair it is one bad inference away from destroying a
      playthrough, and this project has already learned what happens when
      inferred verdicts meet real user state. Repairs stay out of scope until
      the report has been right about a real install more than once.

  19.3 THE THREE STATES, AND WHY THE MAIN MENU IS THE GOOD ONE
      This is the constraint that makes the model schedulable, and it is a
      three-state question rather than a two-state one. The distinguishing
      factor is not "is the process running" but "is the Papyrus VM idle and
      is any save in flight".

      GAME OFF            everything is safe. Nothing is executing.
      MAIN MENU, NO SAVE  the ONE window where both risky operations are safe:
                          the VM is idle, so the functions we hook are not on
                          any stack; and no save is in flight, so the lineage is
                          settled and triage is deterministic.
      IN-GAME (SAVE LOADED) read-only scanning is still safe. Hook changes and
                          save triage are NOT.

      The capability matrix, stated once:

                              OFF      MAIN MENU   IN-GAME
      read-only scan            safe     safe        safe
      save lineage triage       safe     safe        NO
      install / remove hooks    safe     safe        NO
      rebuild hook map          safe     safe        NO
      pre-save gate             n/a      n/a        safe (bounded, read-only)

      THE POINT OF THE MAIN MENU ROW. It is the single window in which the
      program can be reconfigured without a restart and without touching live
      state. That makes it where the drift detector acts automatically rather
      than warning, and it is why "auto-reconfigure" is a real capability here
      rather than something that has to be deferred forever. The earlier
      refusal to hot-hook during play is unchanged -- it is only relaxed to
      "automatically at the main menu", which is a place where nothing is at
      risk.

      The rule generalises carefully: this is "the subsystem we care about is
      idle", NOT "the main menu is universally safe". A future hook inside the
      render loop would invalidate that row entirely, because rendering runs at
      the main menu.

  19.4 TRACE CAPABILITY IS THE POINT
      With capture working, a session is a sequence of telemetry bracketed by
      save markers:

        ... frames ...  [SAVE node: lineage position, health]  ... frames ...

      which yields, for the first time, "this save is corrupt AND here is what
      the game was doing when it was written" -- with the offending mod
      attributable, because the telemetry carries thread and frame context.
      That is the project thesis assembled from both halves, and it is why the
      lineage model is worth designing carefully rather than treating saves as
      files to be checked.

  19.5 CANARY REDUX FOLLOWS FROM THIS
      Canary was specified as "check before saving". Under this model it
      becomes "monitor the chain" -- which can point at WHERE a chain broke,
      rather than inspecting one file in isolation. That is a strictly more
      useful capability, and it falls out of the architecture rather than
      requiring new work.

  19.6 STATUS
      Nothing here is built. The lineage model, the triage classes, the state
      matrix and the trace format are all [DESIGNED]. The only verified input
      is the location map in section 18.1 and the telemetry payload work, and
      the latter is necessary but not sufficient -- the trace half cannot exist
      until a single Papyrus event is captured.

================================================================================
 20. ADJUDICATION: WHAT KIND OF FAILURE, AND THEREFORE WHAT TO DO
   [DESIGNED - the product statement; nothing built]
================================================================================

  WHY THIS SECTION, AND WHY IT IS SEPARATE FROM 19
    Section 19 modelled saves as a lineage. That was correct but too LINEAR: it
    presented a single bad save in a numbered sequence and jumped straight to
    "resume from the previous one". Real save sets are not sequences. A fresh
    character has saves 1-9; a mature one has 158 autosaves plus 8 manual ones.
    Slot numbers are not an ordering, so walking them tells you nothing.

    The real question is not "is this save bad" but "WHAT KIND OF BAD IS THIS",
    because the answer determines the remedy, and one of the two possible
    remedies is a trap.

  20.1 THE VERDICT IS OVER THE WHOLE SET
      A verdict drawn from the first failing save is wrong in a way that looks
      correct. What actually carries the diagnostic signal is the DISTRIBUTION
      of failures across the set:

        every save after 2026-09-14 is bad   -> something changed on that date
        saves 8, 12, 15 bad; 9, 10, 11 fine -> specific and intermittent
        one bad, everything else clean       -> contained
        saves 1-9 all bad, fresh character    -> setup territory, not history
        a brand new character, nothing played -> not a fault at all

      The last case is the one a naive scanner reports as catastrophic, and it
      is the reason "count the bad ones" is not an algorithm. A short, entirely
      corrupt-looking set on a new game is the HEALTHIEST possible state.

      So adjudication reads the whole set, cross-references valid / invalid /
      corrupt / absent, and weighs SEQUENCE TOGETHER WITH TIMESTAMPS AND SLOT
      RANGES. No single file produces a verdict on its own.

  20.2 THE DISTINCTION THAT DECIDES THE ACTION
      Two situations that look identical from one file, and must never be
      treated the same:

        CONTAINED                      PERSISTENT
        one bad save                   bad saves, or a repeating pattern
        cause already gone or one-shot the cause is STILL ACTIVE
        remedy: remove and continue    remedy: fix the CAUSE
        if you only remove: SOLVED     if you only remove: IT RECURS

      Deleting a corrupt save while the cause persists is a trap, and the worst
      part is that it looks like success. The player resumes, plays for a
      while, and loses the slot again. "Not showing up one other time is a
      problem that will re-emerge" is the whole argument for classifying
      before acting.

  20.3 CAUSE CLASSES, AND THE REMEDY EACH ONE PERMITS

        CLASS                        REMEDY                        IS OURS?
        --------------------------   ----------------------------   ---------
        contained corruption         remove the save, resume later   yes, safe
        one specific mod             disable / update / remove it     yes, with
                                                                      attribution
        mod conflict, load order     reorder, insert a patch         yes (KaDag)
        version skew, mod vs game    update mod or pin game         diagnose;
                                                                      the action
                                                                      is the user's
        game engine bug              nothing available             REPORT ONLY
        unclassifiable               say so                        report honestly

      THE LAST TWO ROWS ARE THE POINT. A tool that reports a game bug and
      offers nothing is honest and useful. A tool that guesses "load order"
      from no evidence is worse than useless, because a confident wrong answer
      about someone's save is more damaging than an admission of ignorance.
      Adjudication is allowed to say "I don't know", and the classification
      only advances on evidence.

  20.4 REMEDIES ARE VALIDATED ON A COPY, NEVER ON THE LIVE SAVE
      Any proposed remedy is rehearsed against a COPY of the save set. Only a
      remedy that survives that gets offered. This is G4 applied to data
      instead of to output: fail by refusing to act, never by acting and
      hoping.

      It is also the reason the service is non-game-driving. A diagnostic that
      validates remedies by playing the game is a diagnostic that can destroy
      the state it is diagnosing. Ours never drives the game; it copies, it
      inspects, it rehearses, and it reports.

  20.5 THE SHAPE OF THE PRODUCT
      A full-fledged diagnostic service that reasons about game state WITHOUT
      EVER DRIVING THE GAME. Not a feature inside the game, and not a script a
      user runs by hand: something that is always available, always off to the
      side, and safe to run against a live install precisely because it never
      writes to one except when the user has said yes.

      The promise it can actually keep, stated honestly:
        It cannot promise no data loss.
        It CAN promise BOUNDED, IDENTIFIED, MINUTE-SCALE loss instead of a
        three-day revert -- because the lineage identifies the last good save,
        and the telemetry attributes what changed between it and the bad one.
      That substitution is the whole product. Everything else in this document
      is in service of being able to make it.

  20.6 THE NOTIFICATION, AND WHY IT MUST NOT BE CLICKABLE-THROUGH
      Current Canary behaviour is to WARN AND PERMIT: it reports that files
      failed to load, advises a restart, and then allows play to continue.
      That is worse than either extreme. The user cannot later claim they were
      not told, but they also receive no protection -- and continuing is
      exactly what allows a load failure to reach a save.

      So: strong notification, a clear verdict, and a SHUTDOWN action offered
      as the primary path. One constraint on that action, from section 19.3: a
      shutdown button may only be offered when NO SAVE IS IN FLIGHT, otherwise
      it kills the game mid-write -- the precise failure this product exists to
      prevent. The safe window decides whether the button appears at all.

  20.7 STATUS
      Entirely [DESIGNED]. The classification taxonomy, the distribution
      analysis, the copy-based validation loop and the notification contract
      are all proposals. The only verified input is the location map (18.1) and
      the telemetry payload work, and the latter is necessary but not
      sufficient: attributing a corruption to a mod requires captured
      Papyrus events, of which there are currently none.

 21. THE TEST HARNESS: TIERS, GENERATIONS, AND MODIFIERS
   [DESIGNED - taxonomy corrected by research against a real install]
================================================================================

  21.1 WHY A HARNESS OF ENVIRONMENTS, AND WHAT "SMALL" ACTUALLY MEANT
      The useful unit is not a sandbox, it is a REAL MOD CONFIGURATION. A
      synthetic environment cannot answer the only questions that matter,
      because the system under test is the game. So each env drives the real
      engine -- and containment is what stops the damage leaving the boundary.
      Realism and safety are obtained together, not traded.

  21.2 TIERS -- SIZE AND FIDELITY
        TIER  PURPOSE                                   WRITES EXPECTED
        ----  --------------------------------------   ----------------
        0     harness self-test: our own programs,      yes, freely
              protocols, and the env machinery itself
        1     build / refine our own mods, incl. a       yes -- it is ours
              "Sanctuary Lite" style minimal set
        2     small made space: Sanctuary/Concord       ask first
              sized. Game mechanics, mod verification,
              user creation, troubleshooting
        3     large world: a whole mature save         NEVER
        4     blank: triage, trials, adjudication      yes, expected

      TIER 0 IS A DIFFERENT KIND OF THING. It is not a game environment at all,
      it is a check that the harness works. Keeping it distinct matters: "does
      our code work" and "does the game work" should not share a name or a
      rulebook.

      TIER 1 IS THE NAMED FIRST FIXTURE. A minimal, real, player-shaped load
      order is the correct minimal fixture for a reason beyond size: a few
      ESPs, quick to rebuild, fast to reproduce, and REAL rather than synthetic
      so a verdict means something.

      THE ONE RULE, which replaces five per-tier rulebooks:
        WRITES ARE EXPECTED ONLY IN TIERS 0, 1 AND 4 -- the ones we own
        outright. Everything the user cares about is read-only by default, and
        tier 3 is never written to at all.
      The rule scales when a sixth tier appears.

  21.3 GENERATION IS A SEPARATE AXIS, NOT A MODIFIER
      Found by research against the reference install, after first getting it
      WRONG. An earlier pass concluded "DLC is absent" from finding no
      Data\DLC directory and no cc*.ba2 archives. Both were true and the
      conclusion was false:

        Old Gen  (1.10.163)   DLC as cc*.ba2 archives + Data\DLC\ folders
        Next Gen (1.10.984+)  DLC as .esm STUBS in Data\, load-order critical

      The reference install is Next Gen: 21 vanilla "Fallout4 - *.ba2" and
      ZERO "- DLC" variants, with DLCCoast/DLCNukaWorld/DLCRobot/
      DLCworkshop01-03/DLCUltraHighResolution as .esm. F4SE 1.11.240 confirms
      it.

      So generation changes HOW everything loads, not WHAT is present. A tier-2
      Sanctuary environment exists in both generations and is a DIFFERENT
      environment in each. It therefore sits ABOVE modifiers, and the compat
      matrix in section 11 needs the same axis.

  21.4 LIGHT PLUGINS: EXTENSION BEATS HEADER, AND C8 IS RESOLVED
      The second research finding, which retires an open question from the
      original design (C8) rather than merely adding to it.

      C8 was stuck on whether light plugins occupy 0xFD:0x000 or 0xFE
      subdivision slots. The answer is that the question is malformed: a
      light plugin's type is decided by its FILE EXTENSION, and the header
      flags are irrelevant. Verified on the reference install -- 33 .esl
      files, sampled headers all reading chars=0x0000, i.e. no ESM and no ESL
      bit set at all, yet every one of them is a light master by extension.

      Two consequences, both of which affect triage:
        - THE SURVEY MUST READ EXTENSIONS, not header flags.
        - A TEXT LOAD-ORDER FILE IS EVIDENCE, NOT TRUTH. Per LOOT's own
          documentation, light plugins are LISTED at position FE but actually
          LOAD at the position the load order dictates. So plugins.txt
          misreports where light plugins land, and any adjudication that
          trusted it would misattribute.
      This is section 20's rule applied to a source nobody thinks of as
      uncertain: classification advances on evidence, and some evidence is
      weaker than it looks.

  21.5 MODIFIERS -- AND THE GARDEN OF EDEN NAME COLLISION
      A modifier is a presence that changes what an environment MEANS, so
      triage can attribute correctly rather than calling a missing GoE record
      a fault.

      THE COLLISION, recorded because it has already caused one wrong
      assumption in this project:

        GoE SCRIPT EXTENDER     an F4SE plugin, GardenOfEdenPapyrusExtender
                                (3 MB, PRESENT on the reference install).
                                A PAPYRUS EXTENDER, so it falls under
                                replace-list item 2. WE REPLACE IT.
        GoE CREATION KIT /      the content authoring kit. A PEER TOOL. We do
        G.E.C.K.                not replace it and must never break it.

      Both must keep working while the project is built. The coexistence
      contract applies to both, and the modifier axis has to be able to
      distinguish them -- a G.E.C.K. environment and a GoE-Script-Extender
      environment are different environments.

      Other modifiers, same shape: DLC subset, ENB, Unofficial Patch, and the
      ESP/ESL/ESM mix, which given 21.4 is itself a modifier.

  21.6 THE MODAL IS AN OPTIONAL VIEW, NOT A DEPENDENCY
      G16: PIP-MON must be fully useful with no modal built. Everything that
      matters -- triage, adjudication, the survey, the hook map, every verdict
      -- lives in a library and a CLI first. A modal is a view over an
      already-working capability.

      This is a correction to how this has been framed until now. The modal was
      implicitly treated as the product's front door, which would make an
      unbuilt component load-bearing for the whole project. It is not. A
      missing modal delays a FEATURE; a missing library delays the PROJECT, and
      those are not the same cost.

      So: THE MODAL DRIVES DETERMINISTIC ANSWERS AND REPAIRS using its OWN
      C++ and Python/Rust, running outside game threads. That is what makes the
      answers reproducible -- nothing it does competes with the game for a
      thread, and remedies are rehearsed on a copy before anyone is offered
      them. But the same answers must be obtainable by running a command.

      Consequences, consistent with everything else here:
        - No in-game UI at all. A modal drawn while the VM is mid-script is a
          stall, and it is the failure mode that made MCM a replacement
          target rather than a model.
        - An environment in which our tooling is PRESENT gives the modal a far
          better setup to reason from -- telemetry exists, rather than having
          to be inferred. That advantage is real, and it is an argument for
          the modal, not a reason for it to be required.
        - It may also HELP THE USER BUILD A NEW ENVIRONMENT, in a different
          configuration. A tool that can only inspect a fixed set of envs is
          far less useful than one that can propose and assemble a new one --
          assembled as an explicit action the user confirms, never silently.
          And the assembly itself is a CLI operation, so it works before any
          UI exists.

  21.7 STILL OPEN, AND DELIBERATELY SO
      Two questions this section does not answer, because they are the user's
      judgement rather than a technical consequence:
        - WHEN does the modal escalate between tiers? (proposed: tier 4 for
          trials, tier 2 for verification, tier 0 for self-check, tier 3
          read-only only)
        - WHAT may it write in tier 2? Ask-per-write is safer and tedious; a
          declared manifest is faster and is the thing worth reviewing anyway.

  21.8 CONTAINMENT MUST BE TESTABLE, NOT ASSUMED
      An env boundary that has never been tested is a comment. The first
      containment test needs no game at all: write a file from inside an env,
      assert it did not appear outside. Until that passes, "contained" is a
      claim rather than a property -- and this project has a direct, recent
      example of an untested boundary failing quietly.

  21.9 STATUS
      [DESIGNED] throughout. The taxonomy is decided and the location data is
      verified (18.1, 21.3, 21.4), but no env exists, no adapter is written,
      and containment is untested.

 22. THE EXTENDER RELATIONSHIP
   [DESIGNED - the relationship is settled; the replacement capability is
    still gated on the native-registration viability test (section 14)]
================================================================================

  WHAT AN EXTENDER ACTUALLY IS, FROM RESEARCH
    Before this section existed, section 2 said "we replace extender plugins"
    as a positioning line and never said what that meant mechanically. The
    mechanism is now known, and it is narrower than the line suggests.

    A Papyrus extender's core capability is registering NATIVE GLOBAL
    functions onto EXISTING script types. The reference install proves it:
    PapyrusCommonLibrary registers under System: on VANILLA objects --

      System:Form          GetProperties, SetRace, GetCraftSound, ...
      System:Activator     GetData / SetData
      System:AimModel      GetData
      System:MovementType  GetData / SetData

    So "extender plugin" does not mean a new subsystem. It means: a library
    that adds callable methods to types the game already has, so a .psc can
    call functionality the engine never exposed. The parameter prefixes
    (ak/af/ai/ab/as/aa) are Bethesda's own Hungarian convention for exactly
    these functions.

    This narrows the replacement target usefully:
      - we DO replace the library that registers those natives (po3, PCL,
        GoE Script Extender, and their plugin families), because registering
        callables IS the function they perform
      - we do NOT replace the VM's native-registration mechanism itself, which
        is ours to call, not ours to own

  THE PATTERN WE REFUSE, AND WHY
    The reason the extender ecosystem is a conflict minefield is visible in
    the example above: System:Form is a VANILLA type. An extender adding
    GetCraftSound to it has added it to every Form in the game. If two
    extenders add the same method, the second to load silently wins. Every
    "which script extender do I use" question is really this one collision.

    PIP-MON registers into a namespace we own (PipMon:, section 23.4). It
    does not extend vanilla types -- not System:, not Form, not Actor. This
    is incompatibility-as-feature: we are additive, so we install alongside
    anything and collide with nothing. A diagnostics tool that must coexist
    with every other extender cannot afford to be a contender for vanilla
    methods.

  F4SE'S ROLE, WHICH IS NOT A RUNTIME DEPENDENCY
    F4SE is, in this project:
      - a reference, for how native registration is actually done
      - a backup, to prove our registration path against a working example
      - a verification control in the harness (section 21)
    It is NOT:
      - a runtime dependency. vprobe.dll loads and runs with F4SE absent; this
        was proven live (attach_inject succeeded against a vanilla process)
      - a shipping requirement. The decisive test is a game with no F4SE and
        no extender, where we register a native and call it from Papyrus.

  THE PRIORITY THIS CREATES
    Two replacement targets are not the same size:
      1. our own script extension -- native registration under PipMon:, plus
         the logic loops and helpers built on top of it. THIS IS NEXT, because
         it is the core mechanism the rest of the ecosystem stands on.
      2. a general common-library / patcher engine that integrates existing
         libraries (CommonLibF4, AddressLib) and patches mods. This is LAST.
         It is the largest surface and the least foundational.

    The instinct to start with the general library is understandable -- it is
    the most reusable piece -- but it inverts the dependency. Nothing is
    patched and no library is integrated until we can register a native at
    all, so the registration mechanism is the first thing that must be proven.

  WHAT IS PROVEN, AND WHAT IS NOT
    PROVEN: the mechanism exists and is documented; extenders use it; we can
    observe a real extender doing it (PCL's log).
    NOT PROVEN: that we can register a native into a live VM with no extender
    loaded (the viability test, section 14). Every capability above -- our own
    script extension, the patcher, the library integration -- is contingent on
    that one answer. If registration cannot be done without F4SE, the honest
    conclusion is that the "no runtime dependency" position is not achievable
    for the script-extension half, and the design has to change. That is worth
    knowing before building on it, which is why it is the next experiment
    rather than a later one.

================================================================================
 23. NAMING CONVENTION
   [DECIDED - the convention itself. Nothing built against it yet.]
================================================================================

  WHY THIS IS NOT COSMETIC
    A naming convention is a FUNCTIONAL surface, not tidiness. Two things depend
    on it:
      - TRIAGE. A load order containing `pip-mon.*` is instantly attributable.
        Without a prefix, "which of these 127 plugins is ours" is a question
        the tool has to answer by guessing from content.
      - COEXISTENCE. A registered native that collides with another extender's
        is a load-order conflict we caused. Naming is how we avoid colliding
        BEFORE anything loads.

   23.1 FIVE SEPARATE SURFACES. They are not the same name, and conflating them
       is a bug that already happened: the F4SE plugin-list name was changed
       to "PIP-MON" by mistake, the self-test caught it, and the two had been
       treated as one thing. They are not.
      Each has a different audience and a different collision risk.

  23.2 THE SURFACES
      SURFACE                VALUE               AUDIENCE
      ---------------------  -------------------  ----------------------------
      product / suite        PIP-MON              the user, docs, the
                                                 dashboard title
      native plugin name     PIP-MON              the F4SE plugin list
      runtime binary         vprobe.dll           the OS loader (F4SE shows
                                                 it as "V-Probe")
      Papyrus namespace      PipMon:              the VM, every script
      our own content mods   pip-mon.<name>.esp  load order, triage

      Note the case difference is deliberate and load-bearing:
        PIP-MON      the product. UPPER. Appears in prose and titles.
        PipMon:      the Papyrus NAMESPACE. PascalCase, colon-terminated,
                     because that is Papyrus's own syntax for a script
                     namespace, not a style choice.
        pip-mon.     our content. kebab-case, dotted, matching the
                     convention mod authors already use for their own mods.
        vprobe       the binary. lowercase, because it is a filename.

   23.3 PAPYRUS: NAMESPACES ARE A FILE-SYSTEM CONSTRAINT, NOT A LABEL
      Fallout 4 added Namespaced Identifiers, with a hard rule quoted from
      the compiler reference:
        "Each Identifier of a Namespaced Identifier must be the parent of the
         next Identifier in the File System."
      And the namespace is configured in the CK under File > Preferences >
      Scripts, described as "the name of your namespace without any spaces or
      special characters." So a namespace is a DIRECTORY: Scripts/PipMon/*.psc,
      compiled via a .ppj project, each .psc filename matching the full
      namespaced identifier. "PipMon:GetRuntimeStatus" is a layout, not a
      string choice. PascalCase + no spaces is the scene norm (PapyrusUtil,
      JohnnyPapes); "no spaces" is a hard requirement, not a taste.

   23.4 TWO EXTENSION STYLES -- OURS IS THE SECOND
      Research found the actual mechanism extenders use, and it is NOT what
      the first draft assumed. Papyrus exposes NATIVE GLOBAL functions, which
      an extender registers onto EXISTING script types. The reference install
      proves it -- PapyrusCommonLibrary registers on VANILLA objects:
        System:Form          GetProperties, SetRace, GetCraftSound, ...
        System:Activator     GetData / SetData
        System:AimModel      GetData
        System:MovementType  GetData / SetData
      That is the documented style (parameter prefixes ak/af/ai/ab/as/aa), and
      it is the source of the whole collision problem: two extenders adding a
      method to System:Form are adding it to EVERY Form in the game, and the
      second to load wins.

      OUR STYLE IS THE OTHER ONE. We register into a namespace we own. The
      surface is specified with real signatures in section 24; these are the
      placeholders it promotes (note the Get-prefixed renames):
        PipMon:GetRuntimeStatus()      what is working right now
        PipMon:DiagnoseSave(...)       triage a save, returns a verdict
        PipMon:GetLastAdjudication()   the most recent verdict and its basis
        PipMon:GetResolvedProbes()     how many probes are live, and which
        -- RegisterSink became RegisterForEvents/PollEvent in 24, because a
           fixed poll queue is the substrate a push model later rides on --
      TYPES follow the same rule (land after S1 marshaling, section 24.3):
        PipMon:Event
        PipMon:SaveVerdict
      Additive, collides with nothing, diagnosable if it fails. A diagnostics
      tool that must coexist with every other extender has no business
      mutating vanilla types.

      THE RULE, and it is not optional:
        WE DO NOT EXTEND VANILLA TYPES. Ever. Not System:, not Form, not
        Actor. Everything we register lives in PipMon: and touches nothing
        else.

   23.5 OUR OWN MODS -- kebab-case, and the earlier note was wrong
      An earlier draft claimed the community norm was Title Case with spaces,
      from a handful of samples. Sampling the reference install properly, that
      is wrong: it is overwhelmingly LOWERCASE, with dots and hyphens.
        clean and simple - hangman's alley startup.esp
        commonwealth radio.esp
        companion thoughts overhaul.esp
        00bxm_sortingmod_goty_nextgen_version.esp
        3dscopes-goty.esp
      So the convention is:
        pip-mon.sanctuary-lite.esp      the tier 1 build fixture
        pip-mon.adjudication-test.esp   a test mod
        pip-mon.<topic>.esp             anything else we ship
      This is both the norm AND what triage wants: a lowercase pip-mon.* block
      is identifiable by prefix, filters cleanly, and sorts to a visible
      position. Third-party mods are left exactly as their authors named them;
      the convention is ours and applies only to ours.

   23.6 CROSS-LANGUAGE, AND WHY PyO3 NEEDS NO SPECIAL CASE
      Three languages with disagreeing conventions. What keeps them from
      colliding is that they never share a single string:
        LAYER         CONVENTION                EXAMPLE
        ------------  ------------------------  ------------------------
        Papyrus       PascalCase namespace      PipMon:
        ESP filename  lowercase, dotted         pip-mon.foo.esp
        C++           PascalCase types,         PipmonEntry, f4mon::preflight
                      snake_case_ members
        Python        snake_case                overseer_cli, ipc_client
        Rust          snake_case                vlink-protocol, resolve_vtable_slot
      PyO3 bridges Rust and Python, and both already agree on snake_case, so
      it needs no naming rule of its own -- it inherits two that match. The
      only genuine conversion is Rust snake_case to Python snake_case, which is
      identity. The one place case is chosen deliberately is the Papyrus/ESP
      boundary, settled above: PascalCase for scripts (scene norm), lowercase
      for filenames (scene norm).

   23.7 WHAT THIS BUYS, CONCRETELY
        attribution     every one of our mods identifiable by prefix
        coexistence     no namespace collision with PCL, po3, or F4SE
        triage          a failing save can name the culprit by prefix
        load order      ours group together at a known position
        compat matrix   third-party vs ours is a classification, not a guess

   23.8 STATUS AND THE THINGS STILL TO VERIFY
      The convention is decided and the norms behind it are researched, not
      assumed. Three things remain unverified, all answered by the SAME
      experiment -- registering one native in a game with no F4SE and no
      extenders loaded:
        - that a CUSTOM namespace works in FO4's VM, or is F4SE-provided. The
          compiler reference presents it as a CK feature, so it should be
          native, but registration on a live VM is the only proof.
        - that Native Global registration is reachable that way at all. This
          is the fundamental viability question; everything above is contingent
          on the answer.
        - that a namespace survives load order the way a flat name would. If a
          namespace resolves through the VM's type system, an ordering mistake
          could break calls a flat name would not.
      If the answer is no, the convention still stands but the extension
      strategy does not, and that is worth knowing before building on it.

================================================================================
 24. THE MAIN SCRIPTING ENTRY POINTS -- the PipMon: API
   [DESIGNED - the mechanism is read from source; nothing is built. S0 is the
    viability test that everything else is contingent on.]
================================================================================

  WHY THIS SECTION IS THE CENTER OF THE PROJECT
    Sections 2 and 22 say we replace extender plugins. This is what that
    concretely means: a set of Papyrus-callable functions, registered into
    the game's VM, that scripts can call. It is the deliverable every other
    section feeds. It is also the part with the least precedent outside F4SE,
    so it is specified here down to the struct layout rather than sketched.

  24.1 THE MECHANISM, READ FROM SOURCE
      Ground truth is F4SE's PapyrusNativeFunctions.h. The class chain is:

        BSScript::IFunction              abstract
          └─ NativeFunctionBase          0x50 bytes
               └─ NativeFunction         0x58 bytes, + m_callback

      NativeFunction is the object an extender constructs per API function.
      Its layout IS the registration contract:

        OFFSET  FIELD         MEANING / PAPYRUS EQUIVALENT
        ------  ------------  ---------------------------------------------
        0x10    m_fnName      the function name, e.g. "GetRuntimeStatus"
        0x18    m_className   the class/namespace, e.g. "PipMon"
        0x28    m_retnType    return type
        0x30    m_params      param names + types, numParams/realNumParams
        0x40    m_isStatic    the Papyrus `Global` keyword
        0x42    m_isLatent    the `Function` (latent) keyword
        0x50    m_callback    the raw function pointer -- our code

      Two details carry design weight:
        - m_isStatic at 0x40 is literally the Global in `Native Global`. Our
          functions are Global, so they are callable as PipMon:Foo() from
          anywhere rather than on a script instance.
        - IFunction::kFunctionFlag_NoWait (0x01) is documented in the source
          as "set this only if your function is thread-safe." This collides
          with the section 3 performance rule, and the two together are a
          hard constraint on every callback we write: do not block, do not
          allocate, do not format strings on a game thread.

  24.2 TWO LAYERS -- ONE REGISTRATION CHOKE POINT, N CALLBACKS
      This is the shape of the whole integration, and it is the same shape
      F4SE occupies:

        LAYER A -- REGISTRATION (exactly one entry point)
          A hook on the VM's native-function RESOLUTION. When Papyrus
          resolves a native by (class, name, return, params), the VM asks
          us; we return our NativeFunction. Everything we expose is
          installed through this single point. THIS is the "main scripting
          entry point" -- and it is the exact spot F4SE uses, which is why
          doing it without F4SE is a real experiment and not a given.

        LAYER B -- CALLBACKS (one per function)
          Each function's implementation, reached through m_callback /
          NativeFunction::Run(VMValue*, VirtualMachine*, ..., VMValue*,
          VMState*). Marshals VMValues in, does the work, writes the result
          out.

      The naming research (23.3/23.4) now has a mechanical reason behind it,
      not just a style one: "PipMon" is a FIELD in a struct the VM matches
      on. The namespace is the registration key, so getting it right is
      load-bearing for the VM, not cosmetic.

  24.3 BUILD ORDER -- MECHANISM SEAMS, NOT THE A/B EVENT LINE
      The natural instinct is to jump from "registration works" straight to a
      full event system. That skips the real risk. The honest ladder cuts at
      the places a distinct, separately-falsifiable mechanism begins:

        STAGE  PROVES          EXIT CRITERION
        -----  --------------  --------------------------------------------
        S0     registration    a .psc calls PipMon:GetVersion() -> int and
                 (Layer A)     gets a correct value, with NO F4SE loaded
        S1     marshaling      PipMon:GetStringTest() -> string returns
                 (type bridge)  correctly, THEN the String[] case
        S2     poll model (B)  a script registers for events and drains one
                 (queue)        live event off a real ring
        S3     external evts   a named callback fires (F4SE-style dispatch)
                 (A, on top)

      WHY S1 IS ITS OWN GATE. Returning an Int is nearly free. Returning a
      String[] is genuinely hard -- GoE's own changelog bills a filterable
      String[] native as a feature. Marshaling is the most likely thing to
      surprise us, so it gets its own pass/fail rather than hiding inside
      "events work."

      THE WALL TO WATCH IS S1. If arbitrary-type marshaling turns out to need
      the VM's TYPE-CREATION API and that path is itself F4SE-gated, the
      honest outcome is a NARROWED surface -- perhaps only Int/Bool/Float and
      fixed strings cross the boundary, no String[] -- and the event models
      shrink to match. That is a real design outcome, not a failure, and it
      is exactly why S1 is separate: we learn the SHAPE of the surface before
      S2/S3 are built on an assumption about it.

  24.4 GUARDRAILS THAT MAKE THE HYBRID VALID, NOT JUST OPTIMISTIC
      - NO A BEFORE B. External events (S3) are not started until the poll
        model (S2) is both proven and in active use. Otherwise "hybrid" is
        just premature A.
      - THE QUEUE OBEYS SECTION 3. Fixed-size, packed structs. No strings, no
        allocation, no formatting on a game thread. kFunctionFlag_NoWait is
        set only on callbacks that are genuinely thread-safe.
      - EVERY STAGE SHIPS. S0 and S1 are independently useful (version and
        probe status are callable from the console via cgf), so no stage is
        throwaway and each is a working diagnostic in its own right.

  24.5 THE EVENT MODEL -- B FIRST, THEN A
      HYBRID, B-first, for a reason that is dependency, not preference:
        POLL (B)          needs only the Layer-A hook. A script calls
                          PollEvent() and drains a queue into its own state
                          machine. No string keys, no callback plumbing, and
                          it survives load order trivially, because there is
                          no name to resolve.
        EXTERNAL (A)      F4SE-style: RegisterForExternalEvent(sender, cb)
                          plus dispatch-by-name. A thin adapter OVER the queue
                          S2 already drains. Proves true push semantics, which
                          is strictly harder and only worth paying for once
                          the substrate is solid.

      B-first is also the one that satisfies the zero-extender exit test
      cleanly: if B works behind the single Layer-A hook, we have proven the
      mechanism with the fewest moving parts.

  24.6 THE FUNCTION SURFACE (real signatures; 23.4's five promoted)
      Marshaling tier is noted per function: [I]=Int/Bool/Float only (S0-safe),
      [S]=string, [A]=String[], [T]=custom struct. Anything [A] or [T] waits
      for S1 to pass.

      STATUS / HEALTH -- the S0+S1 smoke surface
        int    GetVersion()                       [I] ABI rev of this surface
        int    GetRuntimeStatus()                 [I] bitfield, see below
        int    GetCapabilities()                  [I] feature negotiation
        string GetStringTest()                    [S] marshaling probe
        String[] GetStringArrayTest()             [A] the hard marshaling case

      SAVE TRIAGE (feeds 19/20; verdict types land after S1)
        SaveVerdict DiagnoseSave(...)             [T] triage a save
        SaveVerdict GetLastAdjudication()         [T] most recent verdict
        int    GetAdjudicationCount()             [I] how many since load

      PROBE INTROSPECTION (feeds the resolver, 4/18)
        int    GetResolvedProbeCount()            [I] Tier-1/2/3 hits
        String[] GetResolvedProbes()              [A] name + how it resolved
        bool   IsHookLive(int aiProbeId)          [I] liveness by id

      EVENTS (S2/S3 only)
        int    RegisterForEvents(int aiMask)      [I] -> token
        Event  PollEvent()                        [T] drain one (S2)
        bool   UnregisterFromEvents(int aiToken)  [I]
        -- S3 adds RegisterForExternalEvent + dispatch-by-name on top --

      LIBRARY / INVENTORY (feeds 10)
        int    GetLibraryCount()                  [I]
        String[] GetLibraryInventory()            [A]

      Capability bits in GetRuntimeStatus() are the same capability bits
      already exposed by PIPMON_Query (PipmonEntry.hpp), so the in-process ABI
      and the Papyrus surface cannot drift: one set of bits, two doors.

  24.7 THE S0 TEST, STATED SO IT CAN PASS OR FAIL
      Layer B (the dispatch core) is BUILT and TESTED -- see 24.8. Layer A
      (the VM hook) is not, and cannot be until a compiler and a live game are
      available. S0 is the precise, falsifiable statement of section 14's
      viability question, and it is the ONLY thing standing between this design
      and its build order:

        Construct a NativeFunction with m_className "PipMon", m_isStatic true,
        and return it from the VM's resolution hook, such that a COMPILED .psc
        calls PipMon:GetVersion() and receives a correct int -- with F4SE
        absent and no extender present.

      A PASS makes sections 19, 20, and the S2/S3 event models buildable on a
      foundation that is real. A FAIL is equally valuable: it would mean the
      "no runtime dependency" position is not achievable for the
      script-extension half, and the design has to change. Both outcomes are
      worth more than the current state of not knowing, which is why this is
      the next experiment rather than a later one.

 25. TOOLCHAIN: PYTHON 3.12 + RUST + PyO3, AND WHO HAS TO INSTALL IT
   [DECIDED - the division of labour and the distribution rule]
   [Adopted from an external architecture note; reconciled against this
    repo's actual state and existing decisions before recording]
================================================================================

  25.0 THE QUESTION THIS SECTION ANSWERS FIRST
      The external note proposed a Python 3.12 + Rust + PyO3 pipeline without
      saying who installs what. That is the wrong order of concern: the tool
      choice is cheap to change, and "do our users need a Rust toolchain" is
      the question that actually constrains the design. Answered in 25.4
      before any crate is chosen, because it eliminates most of the list.

  25.1 WHAT IS ACTUALLY TRUE ON THIS MACHINE TODAY
      Checked, not assumed:
        Python 3.12.10, pip 26.2.1, cargo 1.98.1        [all present]
        maturin                                            [NOT installed]
        overseer_cli/pyproject.toml  already targets py312, ruff target py312,
          mypy python_version 3.12, and depends on textual + rich + structlog
        vlink-protocol crate already exists and is tested (5 tests, green)

      So two thirds of the proposed stack is ALREADY IN USE. This section is
      mostly ratification plus a distribution decision, not a greenfield plan.
      Only maturin is new, and only because PyO3 is not in use yet.

  25.2 WORKLOAD DIVISION, AND THE ONE PLACE THE NOTE WAS WRONG
      The note's tiering is sound in outline. Adopted, with one correction and
      one demotion:

        RUST CORE -- the OUT-OF-PROCESS tier, not the in-process one
          - Kahn topological sort over the load-order graph (petgraph)
          - CBOR/JSON parsing of world_state_cache.cbor manifests
          - V-Link wire decode, already living in vlink-protocol
          - reference validation over data vprobe hands us

        PYTHON 3.12 -- ORCHESTRATION + every user-facing surface
          - TUI dashboard (textual + rich, already dependencies)
          - triage prompts, plain-English telemetry
          - config schemas and session-delta tracking
          - the in-game mini-mod bridge handshake

        PyO3 -- THE BRIDGE BETWEEN THOSE TWO, and only that

        CORRECTION, and it is a real one: the note put vprobe.dll's "memory
        hooks, cell-attach interceptions and zero-copy patching" in the Rust
        tier. That is not adoptable. vprobe.dll is an in-process, x64 native
        library that detours the game's own functions, and it ALREADY owns
        its detour engine (Detour.cpp, Zydis for instruction lengths and
        RIP-relative detection) and its resolver. Moving its hooks to Rust
        would mean two native runtimes, two allocators and two x64 codegen
        models inside one address space, in a process where a mistake is a
        crash rather than an exception. It would also mean the in-game half
        of the project no longer matches the ONLY thing we have proven
        (Layer B, KERNEL32-only imports, no extender dependency).

          THE IN-PROCESS TIER STAYS C++. It is the part that must not fail
          quietly and the part with the most constrained environment.

        DEMOTION, with a reason: "retour or manual Windows API hooking" for
        vprobe.dll. We already have a purpose-built detour engine that the
        self-test exercises (install/trampoline/remove, undersized-leaf
        refusal, null refusal). Adding a general Windows hooking crate to
        replace it would be strictly worse and would reintroduce a native
        dependency in the one tier that has none.

  25.3 CRATES AND LIBRARIES, MARKED BY WHAT THEY ARE FOR
      RUST
        pyo3 (+ maturin)   the FFI bridge. Only if/when Python must call
                           something Rust already does faster than Python can
        petgraph           Kahn's algorithm for the KADAG load-order graph
        serde + ciborium   world_state_cache.cbor and config manifests
        windows-sys        IF the out-of-process tier ever needs Win32
      PYTHON 3.12
        textual + rich     already dependencies. Do not re-litigate.
        pydantic v2        config schema validation, IF the schemas outgrow
                           what struct validation already covers
      REJECTED
        sonic-rs           a redundant second JSON stack next to serde_json
        retour             see 25.2. The detour engine already exists and is
                           tested; this would be a regression.

  25.4 DISTRIBUTION -- THE ANSWER: USERS INSTALL NOTHING
      THE RULE:
        USERS install no Python, no Rust, no PyO3, no toolchain, nothing.
        DEVELOPERS need Python 3.12 and Rust, which is a normal contributor
        requirement and not a user-facing cost.

      Why, and this is the argument rather than the preference:
        A modding tool's install base is a Steam user with a load order, not a
        programmer. Every prerequisite we add is a class of user we lose, and
        for this project specifically the Vortex incident (a state/profile
        mishap costing a working modlist) is a live demonstration of how
        fragile user-side setup already is. Adding "install Rust" to that is
        not a detail; it is a different product.

      So the stack is a BUILD-TIME concern only. Options, best first:
        1. maturin / PyInstaller-style single binary. Rust static-links,
           Python is embedded. One artefact, no prerequisites. This is what
           we are building toward.
        2. A prebuilt wheel on an index, for the people who want a pip
           install and already have a Python.
        3. A portable-app/zip bundle with an embedded interpreter.
        NOT "document the prerequisites and wish them well". If we cannot
        package it, the feature is deferred -- it does not ship as a
        documented setup burden.

      What this rule ALLOWS, which is the reason to state it positively:
        PyO3 and a heavy Rust tier remain freely available, because none of it
        reaches the user as an install step. The rule costs the ROADMAP
        nothing. It only constrains PACKAGING.

  25.5 HOW THE BRIDGE ACTUALLY CROSSES PROCESSES, because the note implied
      one call and there are two
      There is a real subtlety the external note glosses: "query live memory
      states synchronously" implies in-process reach that the external tier
      does not have. In reality there are two distinct paths, and conflating
      them is how a design ends up needing a debugger in production.

        IN-PROCESS (inside the game)
          vprobe.dll, C++. Hooks, the lockless ring, the IPC server. It never
          calls Python. It writes packed structs into a ring and returns. The
          section 3 performance rule is why: no strings, no formatting, no
          allocation on a game thread.

        OUT-OF-PROCESS (the hub)
          V-Link carries packed frames over the named pipe. Python and Rust
          BOTH read this. The hub survives the game's death, which is the
          single most important property in the architecture.

        PyO3 sits BETWEEN Python and Rust INSIDE the out-of-process tier --
        e.g. Python asking the Rust graph engine to topologically sort 127
        plugins. It does NOT bridge the game. Crossing into the game is
        V-Link and vprobe, and that boundary is not negotiable: it is what
        makes a game crash survivable.

  25.6 ORDER OF WORK, and what gates what
      Nothing here blocks the current critical path. S0 (section 24.7) is
      Layer A in C++ and needs none of this.
        1. S0 viability test                          [in progress, unblocked]
        2. the graph engine in Rust (petgraph)        [independent, later]
        3. PyO3 bridge, if/when profiling shows a real Python-side bottleneck
        4. packaging to a single binary               [before any external
                                                       release]
      Step 3 is deliberately LAST among the bridges and is CONDITIONAL on
      measurement. A PyO3 layer added before there is a measured bottleneck is
      a build-system liability and an FFI surface to keep in sync for nothing.
      If Python is fast enough for the graph, the bridge may never be built,
      and finding that out cheaply is the point.

 24.8 STATE: WHAT IS BUILT, AND THE COMPILER DEPENDENCY
   [Layer B BUILT+TESTED / Layer A NOT BUILT / compiler RESOLVED]
================================================================================

      BUILT AND TESTED (the game is not required for any of this)
        - PapyrusApi.hpp / PapyrusApi.cpp -- the Layer B dispatch core. A pure
          mapping from (namespace, name, arity) to a handler. No game headers,
          no F4SE, no VM types, so it is testable with the game absent.
        - 13 natives registered under PipMon:, 3 with live handlers
          (GetVersion, GetRuntimeStatus, GetCapabilities), 10 declared-but-inert.
        - vprobe/papyrus/PipMon.psc -- the surface as a script author sees it,
          all functions `Native Global`.
        - Two new self-test checks, both passing:
            dispatch              routing, refusal semantics, namespace
                                  isolation, table reachability
            script_conformance    the .psc and the C++ table agree in BOTH
                                  directions, with the .psc read and parsed

      WHY THIS ORDER IS NOT ARBITRARY
        The dispatch core is the part we can be CERTAIN about without a VM.
        The routing decision (which handler) is separable from the marshaling
        decision (how a VMValue becomes a slot), so we build and prove the
        first while the second is still unproven. When Layer A is finally
        hooked it becomes "look up in the table, build a NativeFunction" --
        a few dozen lines -- rather than a rewrite. Writing the surface first
        and the hook second is what keeps the risky half small.

      WHAT THE REFUSAL SEMANTICS ENCODE, and why they are tested
        invokeNative() returns false, cleanly, for four distinct situations:
        unknown function, wrong arity, foreign namespace, declared-but-not-
        built. A bad name reaching a real handler is a crash inside the VM, so
        the table exists partly to make that impossible. The foreign-namespace
        case is the coexistence contract made mechanical: System:GetVersion
        must FAIL, because extending a vanilla type is the thing this project
        refuses to do (24.4). That assertion is in the test suite, so the rule
        cannot erode silently.

      THE COMPILER DEPENDENCY -- RESOLVED, and four things it taught us
        The reference machine had no Creation Kit and no G.E.C.K., so there was
        no PapyrusCompiler.exe and no way to produce a .pex. That is now
        fixed: the CK is installed and PipMon.psc compiles to a verified
        PipMon.pex. Worth recording HOW, because each step was a silent or
        misleading failure rather than an honest error:

        1. THE APP ID WAS WRONG, and blamed the wrong thing. 2107 is a RETIRED
           id. Steam's "no licenses" was read as "you are signed out" -- and
           the account was in fact signed in the whole time. The real Fallout 4
           Creation Kit is app 1946160. Lesson: a Steam error naming a LICENSE
           is about the app, not the session. Verify login state before
           concluding anything about the account.

        2. THE COMPILER CANNOT PARSE SPACED PATHS. Its own argument splitter
           breaks on spaces, and both this repo's path and the game's
           "Program Files (x86)" contain them. An absolute path yields "Unknown
           command line argument" or "Improperly formed command line
           argument" with no useful context. The fix is a space-free staging
           directory and relative arguments only. The install directory of the
           CK is ALSO not obvious: installdir is "Fallout 4", so the tool
           installs INTO the game folder rather than beside it.

        3. BASE SCRIPTS AND A FLAGS FILE ARE BOTH REQUIRED. Every script
           implicitly extends ScriptObject, which is not shipped with the
           compiler -- the CK installs its source under Data\Scripts\Source.
           And those base scripts use user flags, so without -f the compiler
           fails at "Unknown user flag hidden". Bethesda's own
           Institute_Papyrus_Flags.flg is referenced by the shipped
           ScriptCompile.bat but is NOT distributed, so papyrus_flags.flg is
           generated from the base sources. Its format is
           "Flag <Name> <index> { <types> }" with // comments -- NOT one word
           per line and NOT semicolon comments; both produce a wall of ANTLR
           errors. The flag list was derived by scanning the base sources, not
           guessed.

        4. A .ppj IS NOT OPTIONAL AND ITS SCHEMA IS GAME-SPECIFIC. The FIRST
           project file used the Skyrim shape (PapyrusCompile/Files); the
           compiler accepted it, reported nothing, and produced NO OUTPUT. A
           green-looking invocation that compiled nothing -- the same failure
           class as the `echo >` bug in the native build, and the reason every
           stage here verifies its artefact instead of trusting an exit code.
           The FO4 schema (PapyrusProject/Imports/Scripts, per the shipped
           PapyrusProject.xsd) is now used.

        5. AND THE ONE THAT WOULD HAVE BEEN EASY TO MISS: THE SCRIPT ITSELF
           MUST BE FLAGGED Native, not just its functions. With
           "ScriptName PipMon" and thirteen Native functions, the compiler
           rejects all thirteen with "cannot be defined as native because the
           script is not flagged as native". The ScriptName line carries
           Native. This is a property of the SURFACE, so it belongs in the
           conformance test's remit, not only in the .psc.

        All five are now encoded in vprobe/papyrus/build_papyrus.bat, which
        stages, compiles, and verifies the PEX magic, and which is stage 2 of
        the build gate. The .pex is a real, committed build artefact.

        This was a TOOLING dependency throughout, never a runtime one. The
        independence claim is untouched: vprobe.dll still imports KERNEL32.dll
        only.

  26. THE TIER MODEL -- WHAT EACH LAYER IS FOR, AND HOW THEY TALK
   [DESIGNED - the discipline is decided; the hallway is partly built]
   [Derived from the library/toolchain discussion; the tier table is the
    normative part and the hallway is explicitly secondary to it]
================================================================================

  26.1 THE TIERS, AND THE TWO COLUMNS THAT BIND THEM
      This table is the architecture. Everything else in this section is in
      service of keeping each row honest.

        Tier  What it is                            Written for   Cost allowed
        ----  ------------------------------------  -----------  --------------
        T0    Fallout4.exe as bytes. The only        accuracy     none: raw
              thing that is actually true.                        addresses, no
                                                                  comfort
        T1    Oracle. Extracts facts from T0:        provenance   slow, allocates
              RTTI names, vtable shapes,                      freely, offline
              prologues, header hashes.
        T2    Library. The facts, queryable.         speed        zero-parse,
              Resolver: (name, build) -> fact.                  zero-alloc
                                                                  in-game
        T3    Surface. The contracts: PIPMON_*,      explicitness versioned,
              the V-Link wire, the PipMon: API.                  refuses cleanly
        T4    Consumer. Dashboard, CLI, Papyrus.     clarity      the user's
                                                                  language

      "Written for" and "Cost allowed" are NOT descriptive. They are the
      constraint that decides a dispute, and they are stated that way on
      purpose: without a written cost ceiling, every layer drifts toward
      comfort, and the whole stack becomes one big blob of convenience.

      THE GOVERNING RULE, which exists because the failure is obvious:
        A LAYER MAY NEVER BE MADE MORE COMFORTABLE THAN ITS COST ALLOWS.

      Concretely, the things that are forbidden:
        - T2 may not carry a formatted string because a consumer would like one
        - T2 may not parse on demand because a hallway could offer "go deeper"
        - T0 may not gain a name we invented, because the name is convenient
        - T1 may not be skipped by going straight from a guess to a hook
      Each of those has been tempting at some point in this project's history,
      and each is how a wrong address becomes a detour in the wrong function.

  26.2 ResolvedFact -- WHY A FACT IS A RECORD AND NOT A NUMBER
      A resolved symbol used to be a bare address. That is why
      PapyrusScript::Execute could sit in the table as a target, come back
      "rejected", and leave nobody able to ask the only question that mattered:
      WHO SAID THIS SYMBOL EXISTS, AND ON WHAT EVIDENCE?

      The answer, it turned out, was nobody. The name was hand-authored above
      the oracle, for a function no one had ever observed in the binary. Every
      fact therefore carries its own justification:

        ResolvedFact {
          name          only if T1 actually OBSERVED it
          rva
          tier          which oracle produced this
          method        rtti | vtable | aob | crossref | addresslib
          confidence    exact | collision-flagged | heuristic
          provenance    the bytes, the RTTI string, or the referencing caller
        }

      THE RULE THIS ENFORCES:
        A fact with no provenance MAY NOT EXIST.

      Hand-authored names are permitted only as QUERIES, never as facts. If T1
      has not observed a symbol, the resolver reports "no oracle has observed
      this", which is a legitimate and useful answer -- and it is the answer
      that would have caught the six phantom targets immediately instead of
      after an afternoon of in-game debugging.

  26.3 PLUGGABLE ORACLES -- THE "STRING OF POSSIBILITIES"
      Extraction methods are interchangeable oracles feeding one interface:

        T1 oracles:  [RTTI scan] [vtable DB] [AOB] [cross-ref] [AddressLib]
              \          |          |        |           /
               \         |          |        |          /
                v-- T2 library: one query interface --v
                        v
                T3 surfaces, T4 consumers

      Adding an oracle yields more facts and requires NO change above T2: no
      layer edit, no format change, no surface version bump. That property is
      the whole argument for the tier split, and it is the modularity this
      project wanted.

      An oracle that disagrees with another does not override it. It reports
      alongside, and the DISAGREEMENT is itself a fact with provenance -- which
      is how build drift becomes visible before it becomes a crash.

  26.4 REFUSE, DO NOT GUESS
      Every boundary in this codebase refuses cleanly rather than approximating,
      and by now that is a demonstrated discipline rather than an intention.
      Observed refusals, all deliberate:
        blob built for a different image      -> refused, text form takes over
        unknown schema version                -> refused
        non-zero reserved header bytes        -> refused
        wrong record stride / truncation      -> refused
        hash collision (ambiguous)            -> treated as a miss
        wrong arity                           -> refused
        foreign namespace (System:...)        -> refused
        declared-but-unbuilt native           -> refused, with a reason
        address that is not a vtable          -> refused by the gate
        thunk slot                            -> refused, caller tries another

      WHY IT MATTERS ENOUGH TO BE A RULE: the failure this prevents is not an
      error message, it is a detour in a function nobody intended, in a process
      where the only symptom is a crash. A wrong answer is worse than no answer,
      so every uncertainty is resolved toward "no answer".

  26.5 THE HALLWAY -- ACCESS, NOT REASON
      There is a navigation layer over the tiers. It is NOT another tier and it
      does NOT define them. It is the way in; the table in 26.1 is the reason
      each door is shaped as it is.

      It is a HALLWAY, not a library, and the distinction is the whole point:

                       LIBRARY                    HALLWAY
        owns data      yes                         no
        answers        "what is the value?"        "where do I go, and can I?"
        stateful       yes                         no
        fails by       throwing                    refusing, politely

      If it ever holds state it has become a library, and it has been misfiled.

      FOUR AMENITIES, all of which SERVE the tiers and none of which justify one
        signage         what exists and what is available (the capability bits)
        depth control   how far in
        provenance      which door, which oracle, what confidence
        polite refusal  a locked door says WHY, in words

      THE CONSTRAINT ON THE HALLWAY, and the reason it cannot become an excuse:
        THE HALLWAY MAY ONLY RENDER OR DESCEND. IT MAY NEVER RAISE A TIER'S
        COST CEILING.

      "Go deeper" means dropping to a LOWER tier (depth 3 reads T0 bytes), not
      making T0 or T2 do user-level work. The tempting failure -- "the hallway
      can format it, so let T2 carry a string" -- is exactly 26.1's rule
      violated with a plausible excuse attached.

      DEPTH IS A PROPERTY OF THE QUERY, NOT OF THE BUILD
        depth 0   one verdict, one line            real-time checks
        depth 1   per-tier summary                 the --summary-only shape
        depth 2   per-fact with provenance         "why did you say that?"
        depth 3   raw bytes / disassembly           opt-in, read-only,
                                                    never on a game thread

      ONE BINARY, BOTH AUDIENCES. Depth 3 is read-only and never runs on a game
      thread, because section 3 forbids work there; a diagnostic that gets more
      expensive because a verbosity was raised is how a monitor causes the
      outage it is monitoring.

      T3 and T4 are therefore BUILT ON the hallway rather than beside it. Today
      they are not: vlink_probe.py --summary-only, Resolver::explain() and
      PipMon:IsHookLive() are three unrelated answers to the same "is it
      working?" question. Under the hallway they are one capability at three
      depths, and the surfaces become views rather than separate
      implementations. That consolidation is a real piece of remaining work,
      and it is recorded as such rather than described as done.

  26.6 WHAT THIS DOES NOT SETTLE
      - which oracles exist beyond the five named, and in what order they are
        trusted when two disagree
      - the ordering policy between a vtable fact and an AOB fact for the same
        symbol
      - whether T2 is one container file or one per game build (26 and the
        multi-install question); the tier rules above hold either way
      - the runtime footprint budget that "zero-alloc in-game" has to fit inside

  17.2 WHY THIS IS NOT A BOUNDARY VIOLATION

      The distinction that keeps this honest: a peer tool is a user choice;
      a dependency is ours. Referencing Unity in a user's workflow costs
      PIP-MON nothing and obliges it to nothing.

  17.3 THE SCOPE LINE - AND WHY IT IS DRAWN HERE
      Not all of this is equally safe to adopt. Divided by what PIP-MON would
      actually have to build:

      SUPPORTABLE (bounded, genuinely useful to a validation tool)
        - READING the intermediate formats: .obj, .fbx, .step, .stl. These
          are documented, open, and a validation tool benefits from knowing
          "this asset was generated, here is its provenance".
        - PROVENANCE: recording that a given asset came from an external
          generator, so a bad frame can be traced to the generating pipeline
          rather than to a mod author. This fits the project's whole thesis -
          attribute problems to their real cause.
        - Geometry sanity checks: degenerate faces, missing normals, scale
          outliers, watertightness. These are exactly the "flag it rather
          than blame papyrus" diagnostics in section 11.

      OPTIONAL INTEGRATION (user opts in, we stay out of the way)
        - Export a provenance sidecar next to a generated asset.
        - Accept a Unity build's output directory as an additional scan root.

      OUT OF SCOPE - and this is where C14 and C17 apply
        - WRITING Bethesda asset containers (.ba2). See C17: read is in
          scope, write is a separate multi-month project.
        - A general Unity-to-Bethesda asset CONVERTER. That is content
          authoring, which section 15.3 explicitly bounds out. PIP-MON is a
          validator and a station, not an exporter.
        - Emulating or reimplementing Unity's material or lighting model.

  17.4 THE LINE, IN ONE SENTENCE
      Validate the OUTPUT of someone else's generator; do not become the
      generator, and do not become the exporter.

  17.5 IF THIS GROWS
      The moment PIP-MON starts writing engine content rather than
      describing and validating it, it has crossed the same line as trying to
      replace the Creation Kit (C14) and the scale of the project changes
      character entirely. Worth a standing check, like C14: would a user who
      has never heard of Unity still benefit from this feature unchanged?

#  OPERATING GUARDRAILS   [DECIDED - these are how the work gets done]
#
#  Not architecture. Not features. These are the rules the work itself obeys,
#  written down because every one of them exists to stop a specific failure
#  that has either already happened or is easy to walk into.
#
#  G1  AN UNVALIDATED IDEA IS NOT A FEATURE.
#      Nothing ships on the strength of having been discussed. "It compiles"
#      is not validation, "the tests pass" is not validation, and "it worked
#      on my machine once" is not validation. The question is always: what
#      check would prove this right, and has that check run? If it has not,
#      the honest status is [DESIGNED], and it stays that way in this file
#      until someone can demonstrate otherwise.
#
#  G2  NEVER PHRASE AN UNMEASURED THING AS A RESULT.
#      "Zero main-loop latency" was proposed as a design property. It is not
#      one, and it is not measurable until a real frame has crossed the pipe.
#      Same rule for frame pacing, overhead, startup cost, and every other
#      number a user could reasonably expect us to be able to defend. Either
#      we have a measurement or we describe the mechanism and say plainly that
#      it is unmeasured. Optimism in a design document becomes a promise in a
#      README, and then it becomes a bug report.
#
#  G3  A FAILED IDEA IS RECORDED, NOT DELETED.
#      When something does not work, it gets an entry here saying what was
#      tried, what happened, and what it taught. A design document that only
#      accumulates successes is not a design document; it is a brochure, and
#      it guarantees the same mistake gets re-made later by someone who cannot
#      see that it was already tried.
#
#  G4  FAIL LOUDLY AND SPECIFICALLY, OR NOT AT ALL.
#      Silent degradation is the worst failure mode available to a diagnostic
#      tool, because the tool's output is trusted. A clean refusal with a
#      sentence explaining what was wrong is worth more than a partial
#      result that looks fine. "Physical disk only" must never be reported as
#      "no conflicts found". "This probe is off" must never be reported as
#      "nothing happened".
#
#  G5  THE IN-PROCESS SURFACE IS THE DANGEROUS PLACE, SO KEEP IT SMALL.
#      Every line of code that runs inside the game process can end a
#      player's save. A crash in a service process costs a relaunch; a crash
#      in the core costs the game and has no supervisor. This is why MCM's
#      overlay, Canary's polling, and Buffout's analysis all belong outside.
#      When in doubt, the feature belongs in a service.
#
#  G6  NEVER HOOK WHAT WE CANNOT VALIDATE.
#      A resolved address is installed only if it survives plausibility
#      checks. An address that fails validation disables its own probe and
#      nothing else. This is not defensive programming -- it is the direct
#      consequence of running inside a process we do not control, where a
#      wrong guess is a crash on the next Papyrus call rather than an error
#      message. See the 8-byte-literal bug in the memory below.
#
#  G7  ONE INSTALLER, MANY SUBSCRIBERS.
#      No component resolves addresses or installs hooks on its own. Not
#      because of tidiness, but because five independent hook sets means five
#      chances to corrupt a vtable, and the failure is unreproducible.
#
#  G8  TEST THE HOSTILE INPUT, NOT THE HAPPY PATH.
#      The dangerous input is never a real executable. It is a truncated
#      download, a 32-bit binary handed to us by mistake, a DLL where the
#      game belongs, a file whose header lies about its own length. A parser
#      tested only on valid input is untested. Fallout 4 is not available on
#      a build machine, so synthetic hostile fixtures are not a convenience,
#      they are the only way to exercise the path that protects us.
#
#  G9  THE PRE-FLIGHT OWNS THE FIRST INSTRUCTION.
#      The build must be identified, the config validated, and the runtime
#      self-tested before the game executes anything. Discovering a bad
#      match after resume costs the player a crash; discovering it here costs
#      them a sentence. This is the whole reason the launcher exists, and it
#      is worth a suspended process to get.
#
#  G10 IF A TEST IS WRONG, SAY SO AND FIX THE TEST.
#      When a self-test failed during the pre-flight build, two of the three
#      causes were in the test and one was in the parser. The temptation is
#      always to relax the assertion until it passes. Each of those three was
#      fixed at the actual cause, and in one case the correct fix was to
#      WEAKEN the test deliberately and record why -- a truncated file that
#      still contains every field we need is genuinely enough to identify a
#      build, and refusing it would have been the bug. The assertion is a
#      claim about the world; when the world disagrees, the claim is what
#      needs examining.
#
#  G11 DO NOT LET A DISAGREEMENT CLOSE ITSELF.
#      A proposal assessed and rejected by an agent is still a proposal. It
#      stays open until the person whose project it is says so. Writing
#      "REJECTED" into this file on an agent's own judgement converted an
#      argument into a decision, and that mistake is not repeated here.
#
#  G12 ONE LOAD PATH, EVEN WHEN ONE IS TEMPORARY.
#      It is tempting to support the F4SE path "for now" alongside the
#      launcher. Every component then has to work in two worlds, and half
#      the codebase ends up F4SE-shaped. The F4SE load path is test
#      scaffolding behind a flag, with an expiry, and it is expected to be
#      deleted. Anything that would make it permanent gets argued against.
#
#  G13 A GATE THAT NEVER OPENS ITS OUTPUT IS NOT A GATE.
#      A build gate reports what the tools claimed, not what is on disk. M10
#      is the proof: a 15-byte file made of the text "vprobe.dll" shipped
#      behind a GATE PASSED, because the corruption happened after the
#      self-test and nothing ever looked at the artefact. Every gate in this
#      project therefore inspects what it produced -- exists, plausible size,
#      correct magic -- before it is allowed to report success. Exit code zero
#      is a claim about the compiler, not about the filesystem.
#
#  G14 NEVER PUT ">" IN A BATCH echo.
#      cmd reads it as a redirection operator and the "message" is written to
#      whatever follows as a filename. This bit us twice, in two different
#      scripts, on the same day: an `echo >>> FAILED` marker, and an
#      `echo vprobe.dll -> path` that destroyed the build output. Use "-", or
#      the word "to", or escape the caret. The habit is the fix; the artefact
#      check in G13 is the safety net.
#
#  G15 NOTHING OUTSIDE THE PROJECT IS EVER WRITTEN TO OR DELETED.
#      Not %LOCALAPPDATA%, not %APPDATA%, not %TEMP%, not %Documents%, not a
#      game install, not a mod manager's state. Build output and scratch files
#      live inside the project directory or nowhere.
#      READ access outside the project stays unrestricted -- reading the user's
#      logs and configs is how this project learns anything useful.
#
#      WHY THIS RULE EXISTS, plainly, because it cost a real evening.
#      During a cleanup, a directory was deleted that turned out to be a stray
#      copy of an entire user profile sitting outside the project. Removing it
#      took out application data: a mod manager's state directory, its profile
#      and modlist, its deploy metadata, and the game configuration that the
#      manager normally virtualises. The visible symptom hours later was
#      "the game is broken", which sent three people -- including an agent --
#      hunting through the wrong subsystem for a long time.
#      The deletion was not subtle and not intended. The trap was that a
#      directory whose NAME looks like a copy of a home directory looks like
#      junk, and a pattern match on a path fragment feels like a safe heuristic
#      right up until it is not.
#
#      THE RULE, OPERATIVELY:
#        - never delete, move, or truncate a path outside the project
#        - never do so on the basis of a path-fragment match
#        - if something outside the project genuinely must change, name the
#          exact absolute paths and get explicit confirmation for those paths
#        - a build or test that wants a scratch directory uses one INSIDE the
#          project, not a temp folder that may later be swept
#      This is G4 and G13 applied to the filesystem rather than to output:
#      fail loudly, and never act on a value you have not inspected.
#
#  G16 THE TOOL MUST BE FULLY USEFUL WITH NO UI BUILT.
#      Everything that MATTERS lives in a library and a CLI first. A modal, a
#      dashboard, a TUI, a notification -- all of those are VIEWS over an
#      already-working capability, never the thing the capability depends on.
#      Concretely: triage, adjudication, the survey, the hook map and every
#      verdict must be reachable from a command line. If the only way to get an
#      answer is to open a window, then the window is load-bearing and the
#      project has an undeclared dependency on a component that does not
#      exist yet.
#      This is the core/service split (G5) applied to presentation rather than
#      to game code, and it is recorded because the failure mode is common and
#      expensive: designing around the UI, putting the logic in the window, and
#      discovering that the genuinely useful parts were all underneath it and
#      now cannot be scripted, tested headlessly, or used from a service.
#      Corollary worth stating separately: a missing modal delays a FEATURE, and
#      a missing library delays the PROJECT. They are not the same cost, and
#      it is easy to spend a long time on the cheap one.
#

#  PAST MISTAKES, RECORDED PER G3
#
#  M1 DETOUR 8-BYTE LITERAL WRITTEN AT THE WRONG OFFSET   [FIXED]
#      An `FF 25 disp32` absolute address literal was written at offset 8 in
#      a 6-byte slot. It overran the trampoline buffer and corrupted adjacent
#      memory. This is the clearest example of G6 in the project's history:
#      the fault was not that the address was wrong, it was that writing at
#      the target was assumed safe. Found by the native self-test, which is
#      the only reason it was found before shipping.
#
#  M2 PAPYRUS STACK DEPTH TRUNCATED AT 255   [FIXED]
#      Stack depth was `u8`, so any script nesting past 255 reported a
#      plausible-looking low number instead of overflowing. Worse than a
#      crash: it produced confident, wrong diagnostics. This is why G1 exists
#      -- the type looked reasonable and every unit test passed, because none
#      of them ran a 256-deep script.
#
#  M3 HAND-WRITTEN x64 DECODER REPLACED WITH ZYDIS   [FIXED]
#      The original prologue decoder mishandled SIB bytes and immediates. It
#      was replaced with a vendored disassembler rather than patched, on the
#      reasoning that a decoder is exactly the kind of code that looks
#      correct and is not. Related: the planner originally decoded past the
#      14 bytes it required, reading whatever followed.
#
#  M4 A TRUNCATED BUILD WOULD HAVE HASHED DIFFERENTLY   [FIXED]
#      The pre-flight originally clamped the header length when a file was
#      cut short, so the same build would produce a different build key
#      depending on whether it had been damaged. A build identity that
#      changes when a file is corrupted is worse than no identity at all: it
#      fails open, quietly, at the one moment the check matters. The parser
#      now requires the declared optional header to be fully present.
#
#  M5 A DLL WAS ACCEPTED AS THE GAME EXECUTABLE   [FIXED]
#      Found by running the tool against a real system DLL rather than only
#      synthetic fixtures. The synthetic cases had all passed. Reminder that
#      test data chosen by the author tests the author's assumptions.
#
#  M6 AN AGENT'S ASSESSMENT WAS WRITTEN AS A DECISION   [FIXED]
#      See G11. Five architectural concerns were reviewed, and three of them
#      were recorded as "ADOPTED" on the agent's own judgement. The
#      corrections are in the audit block below; the lesson is the guardrail.
#
#  M7 IMAGE-BASE LOOKUP: THREE WRONG ANSWERS BEFORE A CORRECT ONE   [FIXED]
#      All three failed identically -- the verification reported "truncated"
#      and the TOCTOU gate failed closed on every honest launch. Recorded
#      because each failure looks like "the process is dead" rather than "you
#      picked the wrong API".
#        1. Assume the standard 0x140000000 preferred base. WRONG: a
#           CREATE_SUSPENDED process is already ASLR-relocated. Measured base
#           here was 0x7ff6c38c0000, so a fixed-address read hits nothing.
#        2. Toolhelp module enumeration. WRONG, and counter-intuitively so:
#           CreateToolhelp32Snapshot(TH32CS_SNAPMODULE) fails with
#           ERROR_PARTIAL_COPY (299) against a suspended process, despite
#           being the API every DLL injector uses. Those injectors call it on
#           an ALREADY-RUNNING process, which is the difference that matters.
#        3. PEB->ImageBaseAddress. CORRECT, once the struct was right.
#           PROCESS_BASIC_INFORMATION must be exactly 48 bytes on x64. Without
#           the explicit padding after UniqueProcessId, MSVC packs it to 40 and
#           the call returns STATUS_INFO_LENGTH_MISMATCH (0xC0000004) -- which
#           reads exactly like "the PEB is not available yet". The padding and
#           a static_assert on sizeof now exist to stop this recurring.
#      Also worth recording: the wrong answer was reached by generalisation
#      from how normal injection works, and it was only a direct measurement
#      against a suspended process that settled it.
#
#  M8 THE LOADER REWRITES ImageBase, SO A FILE HASH CAN NEVER MATCH A
#      PROCESS HASH   [FIXED]
#      Diffing the header block on disk against the same block in a live
#      process gives EXACTLY FOUR differing bytes, all inside the optional
#      header's ImageBase field, which the loader patches in place when it
#      relocates the image.
#      So the obvious design -- hash the headers on disk during pre-flight,
#      hash them again in memory after spawn, compare -- can never succeed. It
#      is not a subtle bug, it is impossible.
#      Fixed by normalising ImageBase to zero on BOTH sides inside one shared
#      function (buildLookupKey), so the two call sites cannot drift apart
#      again. Found only because the test hashed a real live process rather
#      than reading the same file twice.
#      GENERALISATION: any check that compares "what is on disk" against "what
#      is in memory" must first establish which bytes the loader owns. Assume
#      none and it is guaranteed to fail.
#
#  M9 THE HANDSHAKE EVENT MUST EXIST BEFORE INJECTION   [FIXED]
#      Two separate mistakes, both instructive.
#        - The obvious runtime implementation -- CreateEvent, SetEvent,
#          CloseHandle -- DESTROYS the named event when the last handle closes,
#          so there is nothing left for the parent to open.
#        - Creating the event at WAIT time is too late. The runtime's DllMain
#          runs at injection time, while the process is still suspended, so it
#          has already tried to open an event that did not exist yet and will
#          never try again.
#      The parent owns the sync object and creates it before anything can
#      signal it. The runtime only opens and sets. This is also the shape a
#      real readiness handshake should take, so the fix improves the design
#      rather than merely satisfying the test.
#
#  M10 A GREEN GATE SHIPPED A 15-BYTE "DLL"   [FIXED]
#      The most instructive failure in this project's history, because the
#      gate PASSED while producing a broken artefact.
#      In vprobe\build_vprobe.bat the closing message was:
#          echo vprobe.dll  -> %OUT%\vprobe.dll
#      cmd parses the ">" as a REDIRECTION OPERATOR. It did not print a line;
#      it wrote the literal text "vprobe.dll  -\r\n" (15 bytes) over the DLL
#      that had just been linked. Verified by dumping the file: the first
#      bytes were 76 70 72 6F 62 65 2E 64 6C 6C -- the word "vprobe.dll".
#      It failed in the worst possible way: the corruption happens AFTER the
#      self-test runs, so the sequence was self-test PASS -> GATE PASSED ->
#      a corrupt file on disk. Anyone trusting the gate would have shipped it.
#      The irony is not subtle: the SAME class of bug had already been found
#      and fixed in the root build_all.bat an hour earlier, where an
#      `echo >>> FAILED` marker killed the script. Fixing it in one file and
#      walking into it in another is the strongest possible argument for
#      verifying artefacts instead of trusting exit codes.
#      TWO FIXES, because one would not have been enough:
#        1. The redirect is gone, and both build scripts now carry a warning
#           block stating the rule: no ">" in any echo, use "-" or the word to.
#        2. THE GATE NOW INSPECTS ITS OWN OUTPUT. It checks the artefact
#           exists, is at least 1 KiB, and begins with the MZ signature --
#           for vprobe.dll and for all five launcher binaries. This is the fix
#           that matters: it would have caught this regardless of cause, and
#           it catches the next cause too.
#      GENERALISATION: a build gate that never opens the artefact it produced
#      is a gate that can pass for the wrong reason. Exit code zero is a claim
#      about the compiler, not about the filesystem.
#

#  MICROKERNEL FRAMING   [PROPOSED / PARTLY ADOPTED AS DISCIPLINE]
#
#  A suggestion to describe PIP-MON as a microkernel architecture: a thin
#  in-process core (preloader + vprobe) with analysis and UI as independent
#  out-of-process services talking over shared memory.
#
#  WORTH KEEPING AS A DISCIPLINE, NOT AS A LABEL. The useful part is the
#  standing test it supplies:
#      Does this belong in the core, or is it a service?
#  Applied honestly, that test kills three in-process designs already written
#  above: MCM's overlay (a service), Canary's polling (events already exist),
#  and Buffout's analysis (only the minidump write needs to be in-process).
#  It does not merely describe the current design; it explains why the
#  in-process surface is small, and it makes "keep the core minimal"
#  checkable instead of aspirational.
#
#  WHERE THE ANALOGY DOES NOT HOLD -- do not let these harden into assumptions:
#
#    1. PROCESS BOUNDARIES ARE NOT PRIVILEGE BOUNDARIES.
#       A real microkernel's isolation is enforced by hardware; user space
#       cannot address the kernel. vprobe runs with full read/write/execute
#       inside the game process and can corrupt anything it can name. What
#       we actually have is the ordinary kind of isolation: a crash in a
#       service process does not take the game down. That is real and it is
#       most of the value, but it is not a kernel, and the word overstates
#       what protects a player's save.
#
#    2. SERVICES ARE RESTARTABLE. THE CORE IS NOT.
#       This is the difference that matters operationally. If OverseerCLI
#       dies, relaunch it and the game never notices. If vprobe faults inside
#       the game process, the game is gone and nothing supervises a recovery.
#       A microkernel can treat core failure as survivable because something
#       above it can rebuild the core. We have no such supervisor. This
#       argues for LESS in the core, not more, and for a core that is boring
#       enough to audit in one sitting.
#
#    3. "ZERO MAIN-LOOP LATENCY" IS NOT YET A MEASURED CLAIM.
#       Every frame metric crossing the boundary is a shared-memory write
#       performed ON the game thread, plus a context switch for the consumer.
#       That is dramatically cheaper than an in-process extender and cheaper
#       than anything F4SE does, and that is the honest claim. Zero is not
#       supported, and it cannot be supported until the pipe has carried a
#       real frame -- which, per the banner at the top of this file, it has
#       not. Do not promise a number that no measurement exists for.
#
#  STATUS: framing [PROPOSED]; the core/service test is [ADOPTED] as a
#  review heuristic. No code has changed. The core is the next build target
#  for the reason recorded in section 13: every other component's testing
#  depends on the wire format carrying a real frame, and it has not yet.
#

#  ARCHITECTURAL COMPLICATION AUDIT
#
#  STATUS: NOT DECIDED. These are PROPOSALS plus my ASSESSMENT of them.
#  Nothing here is ratified, and nothing here has been implemented.
#
#  Five issues were raised as concerns. For each, this file records the
#  concern and a second opinion -- not a decision. The second opinion is one
#  agent's reasoning and is fallible; where it disagrees with the proposal
#  (A2, A5) that disagreement is LIVE and needs a human to settle it.
#
#  Read the two columns as:
#      "proposal"  = what was suggested
#      "assessment"= what I think, and why, subject to being wrong
#  Nothing below is a commitment. A1 and A3 look right to me and are the
#  cheapest to adopt if you agree. A2 and A5 are contested.
#
#  A1 THE VFS BLIND SPOT (mod managers virtualise Data/)   [PROPOSED]
#      Modern loaders do not overwrite files. MO2 injects usvfs and presents a
#      virtual Data/ tree; Vortex layers differently. Anything that walks the
#      PHYSICAL disk therefore sees the wrong world, and silently so: KaDag
#      would report a clean load order for a save that is actually broken.
#      ASSESSMENT (agrees, not ratified): KaDag would need an Instance Adapter
#      Layer reading the active profile (MO2 instance ini / modlist, Vortex
#      state) and resolving the effective tree BEFORE the DAG is built. Silent
#      wrongness -- a clean-looking load order for a broken save -- is why this
#      is worth doing rather than a nicety. I think this is the most valuable
#      item in the audit and it is genuinely missing from this document.
#      IF ADOPTED, open question: a third-party config format lands on our
#      critical path, so the adapter should fail LOUDLY to "physical only" and
#      say so, rather than degrade quietly.
#      STATUS: UNBUILT, UNTESTED, UNDECIDED. Whether MO2 or Vortex or both is
#      the target has not been chosen.
#
#  A2 AOB vs Address Library        [CONTESTED - needs your decision]
#      Proposal: drop Address Library and have the out-of-process daemon
#      pattern-scan the game's .text section.
#      My assessment says the mechanism is wrong, for three reasons:
#        1. The daemon cannot. It is a different process; that address space
#           does not exist in it. Resolution is in-process by necessity.
#        2. It discards Tier 1. We deliberately run two tiers: AddressLib INI
#           (exact, community-maintained) then AOB (survives an unlisted
#           patch). AOB-only re-derives everything by pattern on every launch,
#           which is slower AND less safe -- an ambiguous pattern that now
#           matches three functions is the worst failure mode in the system.
#        3. The anti-treadmill goal is already met: a new patch normally costs
#           one INI line, not a new binary.
#      The valid half of the observation -- hardcoded offsets would break
#      instantly -- is already handled: that is why the INI tier exists, and
#      why an unresolvable address disables ONE probe rather than the session.
#      STATUS: OPEN. This is a disagreement between the proposal and one agent,
#      not a settled decision. Nothing has been changed or built either way.
#      Note the current code already implements the two-tier design in
#      VersionConfig.hpp, so the default if nobody decides is "no change".
#
#  A3 RING BACKPRESSURE / SCHEDULER STARVATION  [PROPOSED - I agree, see note]
#      The stated failure mode needs one correction: a correct SPSC ring does
#      not overwrite unread data. It is bounded, it reports full, and the
#      PRODUCER chooses the policy. So the real question is what happens at
#      full -- which is what the proposal actually answers.
#      PROPOSED POLICY: fixed-size, never grows, zero allocation in the hot
#      path.
#      LOSSY for high-frequency frame metrics (drop intermediate samples,
#      keep aggregate counters). LOSSLESS for critical events (pre-save,
#      hook install/fail, VM fault). A drop counter is reported to the
#      dashboard so "no data" is never mistaken for "nothing happened".
#      MY ADDITION, offered as a suggestion rather than a requirement: the
#      scheduler-starvation half of this concern is real and unaddressed. If
#      Windows de-prioritises the consumer, samples queue and the ring fills --
#      and a full ring under a de-prioritised consumer is exactly when losing
#      frame data hurts. Worth deciding separately whether the consumer should
#      be normal or high priority, and whether the producer timestamps on
#      write so gaps are visible rather than silent.
#      STATUS: UNBUILT, UNDECIDED.
#
#  A4 PRE-SAVE DEADLOCK / THREAD SAFETY     [PROPOSED - overlaps Rule 3]
#      Agrees with a rule already written before this audit, so no conflict.
#      Raw SuspendThread on a game thread is prohibited: freezing a stack mid
#      critical section is a silent hang, not a clean failure. The proposal's
#      own solution -- a cooperative interruption point where the VM finishes
#      its instruction slice -- is the correct one.
#      POINT WORTH ADDING, and I think this is a real gap in my own rule: a
#      cooperative wait must still be BOUNDED. A save that cannot drain has to
#      fail and report, not wait forever. A pre-save gate with no timeout is a
#      freeze waiting for one bad frame, and a freeze is the exact failure
#      Canary Redux exists to prevent. Rule 3 says HOW to wait, not WHEN to
#      give up.
#      STATUS: Rule 3 is [DECIDED]. The bounded-timeout addition is a
#      [PROPOSAL] and is unbuilt.
#
#  A5 DEFENDER / ANTI-CHEAT HEURISTICS     [PROPOSED - corrected, see note]
#      The concern is reasonable; two specifics in the proposal are wrong.
#        - "sign with a self-signed certificate" does nothing. Self-signed is
#          not trusted by Defender or SmartScreen and is not a mitigation.
#          Real code-signing is the only thing that moves reputation.
#        - CREATE_SUSPENDED is not itself an indicator. Debuggers, profilers
#          and crash handlers all use it. The heuristic fires on a COMBINATION:
#          remote allocation + remote thread + memory-protect change + unbacked
#          executable memory. That four-part set is process hollowing, and it
#          is avoidable by not doing all four.
#      Also worth weighing before over-investing here: Fallout 4 has no
#      serious anti-cheat (no EAC, no BattlEye, single-player), and F4SE has
#      shipped for over a decade without mass quarantine. The real costs are
#      generic injection heuristics and SmartScreen download reputation.
#      SUGGESTED CONSTRAINTS (cheap, and mostly already true of the code):
#      vprobe stays un-obfuscated -- no packing, no shellcode caves, no
#      self-modifying code, no unbacked exec; the V-Link transport is ordinary
#      named-pipe and file-mapping API; the launcher allocates and loads ONE
#      known DLL. If a fourth element of the hollowing set ever gets added,
#      that is a decision to revisit rather than an implementation detail.
#      STATUS: UNBUILT, UNDECIDED. Cheap to adopt if you agree, because most
#      of it is a constraint on code that does not exist yet.
#

#  M11 A SECOND HAND-ROLLED PE PARSER, AND IT LIED   [FIXED]
#      tools/sigcheck.cpp was written with its own PE header structs instead of
#      reusing the launcher's. TimeDateStamp was declared uint16 instead of
#      uint32, which shifted every subsequent field: the tool reported
#      "ts 0x00007fcc" where the validated parser reported 0x6a727fcc, and
#      printed a garbage section table of nine nonsensical entries -- while
#      still exiting successfully and still producing a plausible-looking
#      "0 matches" table.
#      The zeros were almost certainly FALSE. A tool that cannot find the
#      .text section cannot fail to find a signature in it, and the output did
#      not distinguish those two cases at all.
#      Fixed by deleting the duplicate parser and having sigcheck link the
#      launcher's BuildIdentity.cpp directly. parseSections() was added there,
#      with bounds checks, and sigcheck now refuses to report ANY result if the
#      section table comes back empty -- because a zero caused by a parse
#      failure must never be readable as a zero caused by an absent signature.
#      GENERALISATION: for any well-specified structure, a second
#      implementation is a liability with no upside. Reuse the one that has
#      tests. And a scan that finds nothing must be able to prove it searched.

#  M12 A ZERO RESULT AND A BROKEN SEARCH LOOK IDENTICAL   [FIXED]
#      The same incident exposed a deeper problem, and this is the entry worth
#      remembering. sigcheck's first output was "6 zero, 0 unique" from a tool
#      that had not successfully located the section table. Nothing in the
#      output said so, and a reader would reasonably have concluded the
#      signatures were absent when the truth was that the tool was broken.
#      In a project whose entire thesis is DO NOT TRUST A SILENT FAILURE, a
#      tool that reports a clean negative when it has actually failed is the
#      worst possible defect. The fix is structural: sigcheck now exits
#      non-zero and says why when parsing yields no usable sections, and it
#      reports how many executable sections it actually scanned per signature.
#      A negative result must carry its own evidence.

#  1. F4SE                  loader, core DLL injection, version-locked vtable hooks

#  where a decade of progress is available. The load-bearing rule:
#
#      All five in-process capabilities register as SUBSCRIBERS to vprobe's
#      single hook installer. None of them installs a hook of its own.
#
#  One address-resolution surface, one validation path, one place where a bad
#  build is caught. Failures of address resolution stay local to one probe
#  instead of becoming a vtable corruption.
#
#  THE READ/WRITE ASYMMETRY that sets two scope limits:
#      For Bethesda formats, reading is tolerant and writing is exact. A
#      reader may skip what it does not understand; a writer must be
#      byte-perfect or the game misloads silently. So:

#        - Creation Kit: the .psc -> .pex compiler is ours (6, partially).
#          The world editor is NOT (C14).
#      The principle underneath both:
#        PIP-MON owns the artifact formats -- compile, read, validate, analyse.
#        PIP-MON does not own the authoring experience.
#      Creep test: does this produce new game content, or explain existing
#      game behaviour? Produces content = peer tool. Explains = ours.

#  SECTION 27 -- TIER 2 GROUND TRUTH: THE SIX DEAD TARGETS, RESOLVED
#
#  [BUILT+TESTED]  Recorded 2026-09-29. This section closes open decision 1 in
#  the handover and corrects two claims in it.
#
#  WHAT WAS WRONG
#    Six "Tier 3" AOB targets were hand-authored against six Papyrus class
#    names: PapyrusScript::Execute, PapyrusThread::Execute,
#    PapyrusVM::DebugPrint, PapyrusVM::PapyrusVM,
#    PapyrusVM::GetRunningThreadCount, FormData::CellStream. Five of six
#    matched nothing, and the handover recorded the conclusion that the NAMES
#    were wrong rather than stale.
#
#  That conclusion was right, and it is now a measurement rather than an
#    inference. tools/read_rtti.py reads the mangled type-descriptor names the
#    compiler emitted into Fallout4.exe -- 12,262 of them, all in .data, all
#    structurally valid (spare == 0, vftable pointer resolving inside the
#    image), zero rejected candidates.
#
#    The result is unambiguous, and it is a negative result:
#
#      PapyrusScript   absent   0 substring hits, 0 classes of that own name
#      PapyrusThread   absent   0 / 0
#      PapyrusVM       absent   0 / 0
#      FormData        absent   3 substring hits, ALL false friends:
#                                SavedFormData, SavedFormData again inside a
#                                NiTMap template argument, and BGSLoadFormData
#                                -- and 0 classes actually named FormData
#
#    The three FormData hits are why own_name() exists as a separate function
#    from a substring test. A substring search would have reported
#    "FormData: PRESENT" and the whole Tier 2 investigation would have chased
#    a class that does not exist. A wrong answer here is worse than no answer
#    for exactly that reason.
#
#    So the six patterns were not stale. They were written for classes the
#    game does not contain, and no amount of byte tuning could ever have made
#    them match. "5 of 6 unresolved" was indistinguishable, from the outside,
#    from a database that needed refreshing.
#
#  WHAT IS ACTUALLY THERE
#    The scripting VM is BSScript::Internal::VirtualMachine, with
#    BSScript::IVirtualMachine as its interface. Both are in the per-build
#    address database, along with 16 further BSScript interfaces. That gives
#    18 vtable targets, up from 5.
#
#    The mapping from dead target to real class is a ROUTE, not a slot index:
#
#      PapyrusVM::PapyrusVM              -> BSScript::Internal::VirtualMachine
#      PapyrusVM::DebugPrint             -> BSScript::IVMDebugInterface
#      PapyrusScript::Execute            -> BSScript::Internal::CodeTasklet
#                                          / ScriptFunction
#      PapyrusVM::GetRunningThreadCount -> a method of the VM above
#      PapyrusThread::Execute            -> no such class
#      FormData::CellStream              -> no such class
#
#    WHICH SLOT is unsourced and stays that way. A slot index comes from a C++
#    class declaration in declaration order. The vendored CommonLibF4 clone in
#    third_party/ carries vtable ADDRESSES (REL::ID per class) but no BSScript
#    method declarations, so there is no declaration to read an index from.
#    Nothing is hooked on the strength of a guessed index. That is the whole
#    point of 26.4, and it is why "18 targets resolve" and "18 methods are
#    hooked" are very different sentences.
#
#  THE SLOT COUNTS WERE A FICTION
#    The handover recorded "BSScript::IClientVM has 20 vtable slots, the
#    signature says 8". Both numbers were wrong. IClientVM has THREE.
#
#    Measuring it required a rule that is not obvious, and the rule is the
#    real finding here. MSVC lays x64 vtables out back to back with no padding
#    and no sentinel:
#
#        [COL for class N][method][method]...[COL for class N+1][method]...
#
#    so the first 8 bytes after a table's last method are NOT a method -- they
#    are the CompleteObjectLocator the next table needs, and they look exactly
#    like a slot: a pointer into .rdata. Counting until the pointers stop
#    pointing at code therefore runs straight through into the neighbouring
#    classes, and that is where "20" came from.
#
#    The boundary is detected structurally: a slot is the end of this table if
#    it is a CompleteObjectLocator, which requires BOTH a first DWORD of 1
#    (COL_SIG_RTTI64) AND a type-descriptor RVA that resolves to a name
#    beginning ".?A". Two independent conditions, so a run of arbitrary data
#    does not pass. 11 of the 18 tables end on such a locator; the other 7 end
#    on a pointer outside the image, which is a debug string ("Master vers...",
#    "BSS header...") sitting immediately after the table.
#
#    The uniform 8 was over-reading IClientVM and IVMDebugInterface by 5 and 2
#    slots -- past the end, into another class -- and under-reading
#    IVMSaveLoadInterface by 18. Over-reading is the dangerous direction and
#    it is what the runtime validator would have done: a locator mistaken for
#    a method is a detour into an unrelated interface.
#
#    A second correction to the same claim. Many slots in these tables resolve
#    to the SAME address (0x022C46A2 throughout). That is MSVC identical COMDAT
#    folding, and it means "a majority of slots point into executable code" is
#    a weak signal -- the merged stub satisfies it trivially. The validator's
#    real work is the boundary, not the count.
#
#  WHAT WAS BUILT
#    tools/measure_vtable.py -- the same check tools/read_vtable.py performs,
#    but OFFLINE against the file instead of against a running process. That
#    is the whole reason this was not already a gate: a design gate that needs
#    the game running is a gate nobody runs before a release. Tier 1 is allowed
#    to be slow and offline, and nothing about reading a vtable requires a live
#    process.
#
#    It imports PeImage and the RTTI walk from read_rtti.py rather than
#    reimplementing them. Two PE parsers would be two things that can disagree,
#    and the disagreement would be invisible.
#
#    It reads its declared counts out of vprobe/include/Signatures.hpp rather
#    than keeping a list of its own. The table is the declaration and the
#    binary is the measurement; a hardcoded copy here would be a second source
#    of truth, and the two would disagree within a week -- which is how the
#    uniform 8 survived as long as it did.
#
#    vprobe/build_vtables.bat runs it in the build gate: tool self-tests first,
#    then the measurement, failing on any disagreement and printing the
#    boundary evidence for each so the correct number can be READ off the real
#    table rather than guessed. It is wired into build_all.bat and skips
#    cleanly with no game installed, alongside the address blob.
#
#  THE GATES ON THE GATE
#    The tool refuses to report anything at all unless BSScript::IClientVM at
#    0x25B85C8 measures as a vtable whose RTTI name is BSScript::IClientVM.
#    Without that it exits non-zero rather than printing a list, because a
#    tool that is wrong about the one entry it can check has no business
#    answering about the rest.
#
#    It also has 15 of its own self-tests, on synthetic images built in the
#    test: all three MSVC jump-stub forms decoded, non-stub bytes refused, a
#    stub to a non-executable target correctly NOT counted as code, a
#    well-formed locator recognised, a locator with a bogus type descriptor
#    refused, a wrong signature refused, and an RVA inside a section's virtual
#    extent but past its raw data refused.
#
#    That last one changed a threshold. The tool originally required 4 slots,
#    carried over from read_vtable.py where a code-pointer count was the only
#    available evidence. It refused IClientVM, which has three methods, and the
#    gate then correctly refused to report anything -- a correct tool declining
#    to answer because of a threshold inherited from a weaker one. The floor is
#    now 1, because by that point the RTTI walk has already named the class: a
#    table with a locator pointing at a type descriptor IS a vtable by
#    definition, and the count measures it rather than evidencing it. Any
#    floor above 1 is an assumption that interfaces are shaped a particular
#    way, which is the same class of mistake as a hand-authored symbol.
#
#  THE FOUR HOOKS THAT WERE REMOVED
#    PapyrusHooks.cpp installed four detours on four of the dead names, logged
#    "unresolved, probe degraded" on every boot, and could never install. They
#    are deleted rather than disabled, for two reasons.
#
#    A disabled pattern still reads as a target in the tier report, and a
#    report with permanently-dead rows trains the reader to stop reading it.
#
#    And "degraded" was the wrong word. docs/ARCHITECTURE.md states the rule:
#    a disabled hook means a panel shows less, while a silent failure means a
#    panel shows nothing and the game looks healthy. Logging a
#    known-impossible target as degraded put a permanent, already-explained
#    fact on the wrong side of that line, in the one report whose purpose is
#    to be believed. The replacement log line says what is true and why.
#
#  STILL NOT DONE, AND NOT TO BE SKIPPED
#    No vtable slot is hooked. The blocker is narrow and nameable: get a
#    BSScript class declaration with methods in declaration order, and slot
#    indices follow mechanically. The live fork is libxse/commonlibf4 (the
#    pinned Ryan-rsm-McKenzie clone is 1.10.163 and carries no BSScript
#    headers at all). Until that exists, 18 resolved vtables buy identity,
#    extent and existence -- which is what made every other correction in this
#    section possible -- and not a single hooked method.
#
#    Layer A (the VM hook) and S0 (can a compiled .psc call a native with no
#    F4SE) are both still ahead, and S0 still decides design decisions 19 and
#    20. Nothing in this section changes that.
